# สิ่งที่ยังไม่ได้ทำ / ต้องกลับมาคุยต่อ

> ดูสถานะโค้ดจริงล่าสุด (ทำไปแล้วแค่ไหน) ที่ [`05-progress-and-next-steps.md`](05-progress-and-next-steps.md) — เอกสารนี้คือสิ่งที่ยัง "ไม่ตัดสินใจ" ในเชิงออกแบบ/ธุรกิจ ไม่ใช่ backlog เชิงโค้ด

1. **custody-service ตัวจริง** — gRPC/REST + state machine ของ signing request ที่ track ว่า PSBT รอเซ็นจากใครอยู่ **สถานะ**: มี REST skeleton จริงแล้ว (axum, in-memory state machine, idempotent) แต่ยังไม่มี Postgres, ยังไม่เชื่อม HSM/KMS จริง — ดูรายละเอียดใน `05-progress-and-next-steps.md`
2. **mobile-signer-ffi** — รายละเอียด UniFFI binding และการ derive key ให้ตรงกับฝั่ง backend ยังไม่ได้ทำ ตอนนี้ขอบเขตขยายเป็น full hot wallet ตามดีไซน์ "mebit" แล้ว (ดู `design-notes.md`) **ยังต้องตัดสินใจ**: ใช้ `bdk` Rust core จริงตามที่แนะนำ หรือ implement wallet layer เอง — แนะนำ `bdk` เพราะรองรับ coin selection/UTXO/watch-only PSBT แบบ built-in แต่ทีมยังไม่ได้ล็อกเป็นมติ **สถานะโค้ด**: ยังไม่มี hot-wallet layer เลย มีแค่ 3 ฟังก์ชัน mock ฝั่ง vault-signer (`derive_borrower_pubkey`, `compute_vault_address`, `sign_psbt`)
3. **Fund/NAV Ledger ของฝั่งผู้ให้กู้** — ถูกตัดออกจากการคุยรอบนี้ตามคำขอ แต่ต้องทำก่อนขึ้น production เพราะกระทบ liquidation flow โดยตรง
4. **ประเด็นกฎหมาย (ก.ล.ต./ธปท.)** — ถูกตัดออกเช่นกัน แต่สำคัญมาก ควรปรึกษาที่ปรึกษากฎหมายคู่ขนานไปกับการพัฒนา โดยเฉพาะประเด็นกองทุนรวมหลายนักลงทุนที่อาจเข้าข่ายหลักทรัพย์
5. **Threshold ของ LTV** (margin call / liquidation %) — ดีไซน์ "mebit" เสนอค่าที่เป็นรูปธรรมกว่าเดิม คือแจ้งเตือนที่ 65%/72% และบังคับขายที่ 80% (พร้อม borrow preset 25/50/70%) **แต่ยังเป็นข้อเสนอจากฝั่งดีไซน์ ไม่ใช่มติจากทีมความเสี่ยง/ธุรกิจ ต้อง sign-off อย่างเป็นทางการก่อนใช้จริง** **สถานะโค้ด**: `mobile-signer-ffi`/`monitor-service` implement เป็น 3 โซน (ปลอดภัย <50%, เฝ้าระวัง 50–65%, เสี่ยงสูง ≥65%, บังคับขาย 80%) — ยังไม่ได้แยกจุดแจ้งเตือนสองจุด (65% และ 72%) เป็น alert คนละจุดตามดีไซน์ ตอนนี้มีแค่เส้นแบ่งโซนเดียวที่ 65%
6. **ความเป็นอิสระของตัวแทนกองทุน** ผู้ถือคีย์ที่สาม — ต้องกำหนดให้ชัดว่าไม่ใช่คนของแพลตฟอร์มเอง ไม่เช่นนั้น multisig 2-of-3 จะเสียความหมายในทางปฏิบัติ
7. **Policy-constrained auto co-signer** สำหรับฝั่งผู้ให้กู้ (ลด operational latency ตอน liquidation) — ยังไม่ตัดสินใจว่าจะทำหรือไม่
8. **Icon set ของแบรนด์ Mapboss/mebit** — ดีไซน์ปัจจุบันใช้ minimal line icon เป็น placeholder เพราะยังไม่มี icon set จริงของ Mapboss CI ต้องตามงานกับทีม brand
9. **Wallet layer แยกจาก vault layer** — ดีไซน์ทำให้เห็นว่าแอปต้องดูแล BTC สองแบบ (ที่ pledge แล้ว vs ที่ยัง free) ต้องออกแบบให้ชัดว่า UTXO ที่ "free" อยู่ในกระเป๋าแบบ single-sig ธรรมดาของผู้กู้เอง ไม่ใช่ multisig — มีนัยต่อ security model ที่ต้องคิดเพิ่ม (single-sig ส่วนนี้ปลอดภัยน้อยกว่า vault แบบ 2-of-3) **สถานะ**: บันทึกไว้ใน `01-architecture.md` แล้ว แต่ยังไม่มีการ implement จริง (ดูข้อ 2)
10. **Data model ของ `vault-core::keys` (wallet-first pivot)** — วาง type `VaultKey`/`KeySourceType`/`HwVendor` ไว้แล้ว (2026-08-25) เดิมค้าง 3 ข้อที่ถาม **@munich** ตอนนี้ตอบครบแล้ว (2026-08-26):
    - (ก) **แก้แล้ว** — `08-multisig-wallet-spec.md` §2 อยู่ใน repo แล้ว cross-check data model กับ spec ได้ปกติ
    - (ข) **มติ**: เปลี่ยน `derivation_path` จาก `String` เป็น `bitcoin::bip32::DerivationPath` (แบบมี type) แทน — เหตุผล: path พิมพ์ผิดจะ parse ไม่ผ่านทันทีแทนที่จะเป็น string เพี้ยนที่ไม่มีใครจับได้จนกว่าจะเอาไปใช้จริง, `DerivationPath` มี `Display`/`FromStr` อยู่แล้วจึงไม่เสียความสะดวกเรื่องแปลงเป็น string สำหรับ UI/JSON, และตอนนี้คือจังหวะที่แก้ถูกที่สุดเพราะมีแค่ 1 field + 1 test ที่ผูกกับ `String` อยู่ — ต้องแก้ `VaultKey.derivation_path` ใน `keys.rs` ให้ตรงกับที่ `DerivedKey` (Task No.2 "Key derivation ตาม BIP-48") ใช้อยู่แล้ว ไม่ให้เป็นคนละ type กัน
    - (ค) **มติ**: อย่า hardcode coin_type ทั้งสองค่า (`0'` mainnet หรือ `1'` testnet) — ให้ `derive_account_xpub` (Task No.2) รับ parameter `network: bitcoin::Network` แล้วคำนวณ coin_type child number จากตรงนั้นแทน (mainnet → `0'`, อื่นๆ → `1'` ตามธรรมเนียม BIP-44/48) จะได้ถูกต้องอัตโนมัติไม่ว่าจะรันบน environment ไหน — หมายเหตุ: `derivation::BIP48_MULTISIG_PATH` เดิมที่ hardcode เป็น mainnet (`m/48'/0'/0'/2'`) ทั้งที่โปรเจกต์ทดสอบบน testnet ล้วนๆ ตาม `.claude/skills/testnet-workflow/SKILL.md` ถือเป็นความไม่ตรงกันที่มีอยู่ก่อน wallet-first pivot แล้ว ไม่ใช่ปัญหาที่ spec ใหม่สร้างขึ้น
11. **No.2.5 (`VaultCoreError`) ยังปิดไม่สมบูรณ์จนกว่า No.2 จะเสร็จ** — การรวม error type ฝั่ง `keys`/`policy` ทำเสร็จแล้ว (PR #4) แต่ `derivation` module ใน `lib.rs` ยังเป็น mock string จาก term 1 (`derive_child_pubkey(&str, u32) -> String`) ไม่มี `Result`/`bitcoin::bip32` เลย ผลคือ **variant `VaultCoreError::Bip32` ยังไม่มีจุดใช้งานจริงฝั่ง derivation** และ verify step ของ No.2.5 ที่กำหนดให้ทดสอบว่า `derive_child_pubkey` คืน `VaultCoreError::Bip32(_)` ยังทำไม่ได้ ตอนนี้พิสูจน์คุณสมบัติเดียวกันผ่าน `keys::account_xpub_from_mnemonic` แทน (test `out_of_range_account_is_a_bip32_error`) — **เจ้าของ No.2 รับช่วงต่อ**: ตอนเปลี่ยน signature เป็น `Result<DerivedKey, VaultCoreError>` ต้องเพิ่ม test ตัวตรงเข้ามาด้วย จึงจะถือว่า No.2.5 ปิดจริง (มติจากรีวิว PR #4 โดย @Krittanai2933, 2026-08-30)
12. **Key origin ใน descriptor ของ vault-core** (พบระหว่างทำ Jade BLE, 2026-09-30) — `descriptor::build_multisig_descriptor` สร้าง descriptor โดยไม่มี key origin (`[fingerprint/path]`) แต่ hardware wallet หา key ของตัวเองใน PSBT จาก `bip32_derivation` ซึ่งต้องมี master fingerprint และ full path ของแต่ละ key ตอนนี้ harness `jade-hw-test roundtrip` สร้าง descriptor แบบมี origin เองแล้วเทียบ address กับของ vault-core ทีละ index (ตรงกันทุกตัว) **ต้องตัดสินใจ (เจ้าของ `descriptor` — คนที่ 1)**: จะให้ `build_multisig_descriptor` รับ key origin ด้วยหรือไม่ ก่อนมีโค้ดสร้าง PSBT จริงของ vault — การแก้ signature ถือเป็น breaking change ของ vault-core ตาม `CLAUDE.md` จึงไม่ได้แก้ไปในงานนี้
13. **Register multisig บน Jade (`register_multisig`)** — ไม่จำเป็นต่อการเซ็น (ยืนยันทั้งจาก firmware และจากเครื่องจริง) แต่ถ้าไม่ register Jade จะแสดง change output ของ vault เป็น output ธรรมดา ผู้ใช้จึงตรวจไม่ได้ว่า change กลับเข้า vault ของตัวเองจริง **ยังต้องตัดสินใจ**: จะ register ตอนประกอบ vault หรือไม่ (มีผลต่อ UX และต้องตั้งชื่อ wallet บน Jade ไม่เกิน 16 ตัวอักษร)
14. **ความเสี่ยง Phase 1: `btleplug` บน Android** — ตัดสินใจแล้ว (2026-09-30) ให้ Rust เป็นเจ้าของ BLE บนมือถือ (`jade-ble` ผ่าน UniFFI แทน `react-native-ble-plx`) แต่ `btleplug` บน Android ต้อง build แบบ Rust+Java (jni-utils + droidplug, เรียก `btleplug::platform::init(env)` ผ่าน JNI, กฎ ProGuard — ตาม README ของ btleplug) และยังไม่เคยทดสอบบน Android เลย (iOS ใช้ backend CoreBluetooth ตัวเดียวกับที่ทดสอบบน macOS แล้ว) **ควร spike ตั้งแต่ต้น Phase 1** — ถ้าไม่ไหว `JadeSession` ไม่มี I/O อยู่แล้ว จึงย้ายกลับไปให้ RN เป็นเจ้าของ BLE ได้โดยไม่ต้องแก้ protocol
15. **Firmware 1.0.41 ของ Jade reboot เมื่อ PSBT ที่เซ็นแล้วยาวเป็นพหุคูณของ 3008 ไบต์พอดี** (พบจากการอ่าน source ของ firmware ระหว่างรีวิวก่อนเปิด PR ของ `jade-ble`, 2026-10-01 — ยังไม่เคยเกิดบนเครื่องจริง) — `sign_psbt_process()` ใน `main/process/sign_psbt.c` คิดจำนวนท่อนเป็น `bytes_len / 3008 + 1` แทนการปัดขึ้น ถ้าความยาวหาร 3008 ลงตัว ท่อนสุดท้ายจะว่าง และ `JADE_ASSERT(chunk < bytes + bytes_len)` ทำให้ Jade reboot ตอนที่ host ขอท่อนนั้น (host เห็นเป็น `the Jade disconnected` หลังจากผู้ใช้กดยืนยันไปแล้ว) เกิดราว 1 ใน 3008 ครั้งของ PSBT ที่ยาวเกิน 3 KB และเซ็น PSBT เดิมซ้ำก็เจอซ้ำ เพราะลายเซ็นของ Jade deterministic — ณ จุดนั้น host ได้ PSBT ครบแล้ว จึงเลี่ยงฝั่ง host ได้ (ไม่ขอท่อนที่ว่าง แล้วปิดการรอของ Jade ด้วย `get_extended_data` ที่ field ไม่ตรง ซึ่ง firmware ตอบ `-32001` แล้วออกจาก `sign_psbt` ตามปกติ) **มติ (2026-10-01)**: ยังไม่ทำ workaround ใน PR ของ `jade-ble` — บันทึกไว้ที่นี่และใน README ของ `jade-ble` แล้วรายงาน upstream ที่ `Blockstream/Jade` ก่อน ถ้าจะทำ workaround ต้องทดสอบกับเครื่องจริงด้วย PSBT ที่จงใจปรับความยาวให้ PSBT ที่เซ็นแล้วยาวเป็นพหุคูณของ 3008 พอดี
