# สิ่งที่ยังไม่ได้ทำ / ต้องกลับมาคุยต่อ

> ดูสถานะโค้ดจริงล่าสุด (ทำไปแล้วแค่ไหน) ที่ [`05-progress-and-next-steps.md`](05-progress-and-next-steps.md) — เอกสารนี้คือสิ่งที่ยัง "ไม่ตัดสินใจ" ในเชิงออกแบบ/ธุรกิจ ไม่ใช่ backlog เชิงโค้ด

1. **custody-service ตัวจริง** — gRPC/REST + state machine ของ signing request ที่ track ว่า PSBT รอเซ็นจากใครอยู่ **สถานะ**: มี REST skeleton จริงแล้ว (axum, in-memory state machine, idempotent) แต่ยังไม่มี Postgres, ยังไม่เชื่อม HSM/KMS จริง — ดูรายละเอียดใน `05-progress-and-next-steps.md`
2. **mobile-signer-ffi** — รายละเอียด UniFFI binding และการ derive key ให้ตรงกับฝั่ง backend ยังไม่ได้ทำ ตอนนี้ขอบเขตขยายเป็น full hot wallet ตามดีไซน์ "mebit" แล้ว (ดู `design-notes.md`) **ยังต้องตัดสินใจ**: ใช้ `bdk` Rust core จริงตามที่แนะนำ หรือ implement wallet layer เอง — แนะนำ `bdk` เพราะรองรับ coin selection/UTXO/watch-only PSBT แบบ built-in แต่ทีมยังไม่ได้ล็อกเป็นมติ **สถานะโค้ด**: ยังไม่มี hot-wallet layer เลย มีแค่ 3 ฟังก์ชัน mock ฝั่ง vault-signer (`derive_borrower_pubkey`, `compute_vault_address`, `sign_psbt`)
3. **Fund/NAV Ledger ของฝั่งผู้ให้กู้** — ถูกตัดออกจากการคุยรอบนี้ตามคำขอ แต่ต้องทำก่อนขึ้น production เพราะกระทบ liquidation flow โดยตรง
4. **ประเด็นกฎหมาย (ก.ล.ต./ธปท.)** — ถูกตัดออกเช่นกัน แต่สำคัญมาก ควรปรึกษาที่ปรึกษากฎหมายคู่ขนานไปกับการพัฒนา โดยเฉพาะประเด็นกองทุนรวมหลายนักลงทุนที่อาจเข้าข่ายหลักทรัพย์
5. **Threshold ของ LTV** (margin call / liquidation %) — ดีไซน์ "mebit" เสนอค่าที่เป็นรูปธรรมกว่าเดิม คือแจ้งเตือนที่ 65%/72% และบังคับขายที่ 80% (พร้อม borrow preset 25/50/70%) **แต่ยังเป็นข้อเสนอจากฝั่งดีไซน์ ไม่ใช่มติจากทีมความเสี่ยง/ธุรกิจ ต้อง sign-off อย่างเป็นทางการก่อนใช้จริง** **สถานะโค้ด**: `mobile-signer-ffi`/`monitor-service` implement เป็น 3 โซน (ปลอดภัย <50%, เฝ้าระวัง 50–65%, เสี่ยงสูง ≥65%, บังคับขาย 80%) — ยังไม่ได้แยกจุดแจ้งเตือนสองจุด (65% และ 72%) เป็น alert คนละจุดตามดีไซน์ ตอนนี้มีแค่เส้นแบ่งโซนเดียวที่ 65%
6. **ความเป็นอิสระของตัวแทนกองทุน** ผู้ถือคีย์ที่สาม — ต้องกำหนดให้ชัดว่าไม่ใช่คนของแพลตฟอร์มเอง ไม่เช่นนั้น multisig 2-of-3 จะเสียความหมายในทางปฏิบัติ
7. **Policy-constrained auto co-signer** สำหรับฝั่งผู้ให้กู้ (ลด operational latency ตอน liquidation) — ยังไม่ตัดสินใจว่าจะทำหรือไม่
8. **Icon set ของแบรนด์ Mapboss/mebit** — ดีไซน์ปัจจุบันใช้ minimal line icon เป็น placeholder เพราะยังไม่มี icon set จริงของ Mapboss CI ต้องตามงานกับทีม brand
9. **Wallet layer แยกจาก vault layer** — ดีไซน์ทำให้เห็นว่าแอปต้องดูแล BTC สองแบบ (ที่ pledge แล้ว vs ที่ยัง free) ต้องออกแบบให้ชัดว่า UTXO ที่ "free" อยู่ในกระเป๋าแบบ single-sig ธรรมดาของผู้กู้เอง ไม่ใช่ multisig — มีนัยต่อ security model ที่ต้องคิดเพิ่ม (single-sig ส่วนนี้ปลอดภัยน้อยกว่า vault แบบ 2-of-3) **สถานะ**: บันทึกไว้ใน `01-architecture.md` แล้ว แต่ยังไม่มีการ implement จริง (ดูข้อ 2)
10. **Data model ของ `vault-core::keys` (wallet-first pivot)** — วาง type `VaultKey`/`KeySourceType`/`HwVendor` ไว้แล้ว (2026-08-25) เดิมค้าง 3 ข้อที่ถาม **@munich** ตอนนี้ตอบครบแล้ว (2026-08-26):
    - (ก) **แก้แล้ว** — `08-multisig-wallet-spec.md` §2 อยู่ใน repo แล้ว cross-check data model กับ spec ได้ปกติ
    - (ข) **มติ**: เปลี่ยน `derivation_path` จาก `String` เป็น `bitcoin::bip32::DerivationPath` (แบบมี type) แทน — เหตุผล: path พิมพ์ผิดจะ parse ไม่ผ่านทันทีแทนที่จะเป็น string เพี้ยนที่ไม่มีใครจับได้จนกว่าจะเอาไปใช้จริง, `DerivationPath` มี `Display`/`FromStr` อยู่แล้วจึงไม่เสียความสะดวกเรื่องแปลงเป็น string สำหรับ UI/JSON, และตอนนี้คือจังหวะที่แก้ถูกที่สุดเพราะมีแค่ 1 field + 1 test ที่ผูกกับ `String` อยู่ — ต้องแก้ `VaultKey.derivation_path` ใน `keys.rs` ให้ตรงกับที่ `DerivedKey` (Task No.2 "Key derivation ตาม BIP-48") ใช้อยู่แล้ว ไม่ให้เป็นคนละ type กัน
    - (ค) **มติ**: อย่า hardcode coin_type ทั้งสองค่า (`0'` mainnet หรือ `1'` testnet) — ให้ `derive_account_xpub` (Task No.2) รับ parameter `network: bitcoin::Network` แล้วคำนวณ coin_type child number จากตรงนั้นแทน (mainnet → `0'`, อื่นๆ → `1'` ตามธรรมเนียม BIP-44/48) จะได้ถูกต้องอัตโนมัติไม่ว่าจะรันบน environment ไหน — หมายเหตุ: `derivation::BIP48_MULTISIG_PATH` เดิมที่ hardcode เป็น mainnet (`m/48'/0'/0'/2'`) ทั้งที่โปรเจกต์ทดสอบบน testnet ล้วนๆ ตาม `.claude/skills/testnet-workflow/SKILL.md` ถือเป็นความไม่ตรงกันที่มีอยู่ก่อน wallet-first pivot แล้ว ไม่ใช่ปัญหาที่ spec ใหม่สร้างขึ้น
11. **No.2.5 (`VaultCoreError`) ยังปิดไม่สมบูรณ์จนกว่า No.2 จะเสร็จ** — การรวม error type ฝั่ง `keys`/`policy` ทำเสร็จแล้ว (PR #4) แต่ `derivation` module ใน `lib.rs` ยังเป็น mock string จาก term 1 (`derive_child_pubkey(&str, u32) -> String`) ไม่มี `Result`/`bitcoin::bip32` เลย ผลคือ **variant `VaultCoreError::Bip32` ยังไม่มีจุดใช้งานจริงฝั่ง derivation** และ verify step ของ No.2.5 ที่กำหนดให้ทดสอบว่า `derive_child_pubkey` คืน `VaultCoreError::Bip32(_)` ยังทำไม่ได้ ตอนนี้พิสูจน์คุณสมบัติเดียวกันผ่าน `keys::account_xpub_from_mnemonic` แทน (test `out_of_range_account_is_a_bip32_error`) — **เจ้าของ No.2 รับช่วงต่อ**: ตอนเปลี่ยน signature เป็น `Result<DerivedKey, VaultCoreError>` ต้องเพิ่ม test ตัวตรงเข้ามาด้วย จึงจะถือว่า No.2.5 ปิดจริง (มติจากรีวิว PR #4 โดย @Krittanai2933, 2026-08-30)
12. **Key origin ใน descriptor ของ vault-core** (พบระหว่างทำ Jade BLE, 2026-09-30) — `descriptor::build_multisig_descriptor` สร้าง descriptor โดยไม่มี key origin (`[fingerprint/path]`) แต่ hardware wallet หา key ของตัวเองใน PSBT จาก `bip32_derivation` ซึ่งต้องมี master fingerprint และ full path ของแต่ละ key ตอนนี้ harness `jade-hw-test roundtrip` สร้าง descriptor แบบมี origin เองแล้วเทียบ address กับของ vault-core ทีละ index (ตรงกันทุกตัว) **ต้องตัดสินใจ (เจ้าของ `descriptor` — คนที่ 1)**: จะให้ `build_multisig_descriptor` รับ key origin ด้วยหรือไม่ ก่อนมีโค้ดสร้าง PSBT จริงของ vault — การแก้ signature ถือเป็น breaking change ของ vault-core ตาม `CLAUDE.md` จึงไม่ได้แก้ไปในงานนี้
13. **Register multisig บน Jade (`register_multisig`)** — ไม่จำเป็นต่อการเซ็น (ยืนยันทั้งจาก firmware และจากเครื่องจริง) แต่ถ้าไม่ register Jade จะแสดง change output ของ vault เป็น output ธรรมดา ผู้ใช้จึงตรวจไม่ได้ว่า change กลับเข้า vault ของตัวเองจริง **ยังต้องตัดสินใจ**: จะ register ตอนประกอบ vault หรือไม่ (มีผลต่อ UX และต้องตั้งชื่อ wallet บน Jade ไม่เกิน 16 ตัวอักษร)
14. **ความเสี่ยง Phase 1: `btleplug` บน Android** — ตัดสินใจแล้ว (2026-09-30) ให้ Rust เป็นเจ้าของ BLE บนมือถือ (`jade-ble` ผ่าน UniFFI แทน `react-native-ble-plx`) แต่ `btleplug` บน Android ต้อง build แบบ Rust+Java (jni-utils + droidplug, เรียก `btleplug::platform::init(env)` ผ่าน JNI, กฎ ProGuard — ตาม README ของ btleplug) และยังไม่เคยทดสอบบน Android เลย (iOS ใช้ backend CoreBluetooth ตัวเดียวกับที่ทดสอบบน macOS แล้ว) **ควร spike ตั้งแต่ต้น Phase 1** — ถ้าไม่ไหว `JadeSession` ไม่มี I/O อยู่แล้ว จึงย้ายกลับไปให้ RN เป็นเจ้าของ BLE ได้โดยไม่ต้องแก้ protocol
    **สถานะ (2026-10-21): spike ผ่านบน emulator และกับวิทยุจริงบน Galaxy S25 FE (Android 16) หนึ่งเครื่องกับ Jade หนึ่งตัว ส่วน Trezor Safe 7 ยังไม่ได้ทดสอบบน Android** **อัปเดต (2026-10-23): ผ่านบน POCO X3 NFC (Android 11, MIUI 12.5) ทั้ง Jade และ Trezor Safe 7 (firmware 2.13.0, MTU 247) ส่วน Galaxy S25 FE ยังไม่ได้ทดสอบกับ Safe 7**
    - Java ของ btleplug 0.13.3 มี 28 ไฟล์ (รวม `jni-utils` ไว้ในตัวแล้ว) คอมไพล์ใน Kotlin Toolchain ได้โดยไม่ต้องตั้งค่า `ffi.sh` คัดลอกเข้า `app/mobileSignerFfi/src@android` และ `ffi.sh check` เทียบกับเวอร์ชันที่ cargo resolve
    - JNA ไม่เรียก `JNI_OnLoad` จึงต้องเรียก `System.loadLibrary("mobile_signer_ffi")` ก่อนใช้ Bluetooth ไม่เช่นนั้นทุก export ตอบ `Unsupported` (วัดบน prototype)
    - วัดบน emulator API 36 (arm64) กับ debug build ของโค้ดรอบที่สองก่อนแพตช์ Gobley: กล่องขอสิทธิ์ขึ้น, อนุญาตแล้วสแกน 4 วินาทีได้ `NotFound` (adapter เสมือนไม่มีอุปกรณ์), ปฏิเสธแล้วได้ `PermissionDenied`, ไม่ crash รอบแรกรัน `cancel-connect:jade:500` ด้วย ส่วนรอบหลังบนโค้ดรอบที่สองล่าสุดรันซ้ำ `jade`, `ffi`, `cancel` และ `trezor` ไม่ได้รัน emulator หลังแพตช์ Gobley R8 release build ผ่านเมื่อเพิ่ม `-dontwarn java.awt.**` เพราะ JNA อ้าง class ของ AWT APK ที่ minify แล้วเคยรัน `ffi` และสแกนบน emulator ในโค้ดรุ่นก่อนที่จำกัดโพรบให้เฉพาะ debug build ส่วน release build ของโค้ดปัจจุบัน (2026-10-22) ตรวจแค่ build และเนื้อใน dex (Java 28 class, JNA และ binding ที่ generate)
    - Galaxy S25 FE (SM-S731B, Android 16, API 36, One UI 8.5, page ของหน่วยความจำ 4 KB) กับ Jade Core `Jade BE0184` ใน debug build: ปฏิเสธสิทธิ์ครั้งแรกแล้ว `ffi` ยังรันได้ ครั้งที่สองแล้ว `jade` ได้ `PermissionDenied` และไม่ crash, สวิตช์ Bluetooth ปิดแต่ adapter ค้างที่ `BLE_ON` ได้ `NotFound` ไม่ใช่ `BluetoothOff` (ข้อ 30), จับคู่ครั้งแรกผ่านกล่องโต้ตอบของระบบบนมือถือสองขั้นแล้ว `info` ได้ค่าเดียวกับบน Mac และ iPhone, รอบต่อมาไม่มี prompt, `cancel` กับ `cancel-connect` ผ่าน (รอบท้ายสุดบน wrapper ปัจจุบันที่ free ใน `finally` ตัวเดียว) และ build ที่ถอด guard ของลิงก์ออกล้มตามที่คาด (ข้อ 34) หลักฐานดิบอยู่ใน `~/mebit-ble-evidence/2026-10-21/android-sm-s731b/` นอก repo
    - ยังไม่ได้ทำ: Android รุ่นอื่น (ทดสอบเครื่องเดียว), API 30 ลงไป (ไม่มี image), เครื่องที่ใช้ page 16 KB (Galaxy เครื่องนี้ใช้ 4 KB), `trezor-ble` บน Android และ release build ที่รันบนเครื่องจริง
15. **Firmware 1.0.41 ของ Jade reboot เมื่อ PSBT ที่เซ็นแล้วยาวเป็นพหุคูณของ 3008 ไบต์พอดี** (พบจากการอ่าน source ของ firmware ระหว่างรีวิวก่อนเปิด PR ของ `jade-ble`, 2026-10-01 — ยังไม่เคยเกิดบนเครื่องจริง) — `sign_psbt_process()` ใน `main/process/sign_psbt.c` คิดจำนวนท่อนเป็น `bytes_len / 3008 + 1` แทนการปัดขึ้น ถ้าความยาวหาร 3008 ลงตัว ท่อนสุดท้ายจะว่าง และ `JADE_ASSERT(chunk < bytes + bytes_len)` ทำให้ Jade reboot ตอนที่ host ขอท่อนนั้น (host เห็นเป็น `the Jade disconnected` หลังจากผู้ใช้กดยืนยันไปแล้ว) เกิดราว 1 ใน 3008 ครั้งของ PSBT ที่ยาวเกิน 3 KB และเซ็น PSBT เดิมซ้ำก็เจอซ้ำ เพราะลายเซ็นของ Jade deterministic — ณ จุดนั้น host ได้ PSBT ครบแล้ว จึงเลี่ยงฝั่ง host ได้ (ไม่ขอท่อนที่ว่าง แล้วปิดการรอของ Jade ด้วย `get_extended_data` ที่ field ไม่ตรง ซึ่ง firmware ตอบ `-32001` แล้วออกจาก `sign_psbt` ตามปกติ) **มติ (2026-10-01)**: ยังไม่ทำ workaround ใน PR ของ `jade-ble` — บันทึกไว้ที่นี่และใน README ของ `jade-ble` แล้วรายงาน upstream ที่ `Blockstream/Jade` ก่อน ถ้าจะทำ workaround ต้องทดสอบกับเครื่องจริงด้วย PSBT ที่จงใจปรับความยาวให้ PSBT ที่เซ็นแล้วยาวเป็นพหุคูณของ 3008 พอดี
16. **`trezor-client` ใช้กับ Safe 7 ผ่าน BLE ไม่ได้** (พบระหว่างทำ No.5, 2026-10-01) — `09-wallet-mvp-buildplan.md` §4–5 เดิมเขียนว่าใช้ `trezor-client` ทางการได้เลย "ความเสี่ยงต่ำ" แต่ตรวจ source จริงแล้ว (trezor-firmware `c33f815`, `trezor-client` 0.1.6) ไม่เป็นอย่างนั้น

28. **`build_multisig_descriptor` ของ vault-core รับ xpub ซ้ำและ xpub คนละ network ได้** (2026-10-20) — พบตอนห่อด้วย UniFFI และยืนยันด้วยการรันจริง: `build_multisig_descriptor(&[Xpub], k)` ไม่เรียก `Descriptor::sanity_check()` (ตัวที่ปฏิเสธคีย์ซ้ำ) จึงสร้าง address ให้ 2-of-3 ที่มี xpub ซ้ำได้ และรับ `xpub` ปนกับ `tpub` ได้โดยไม่ error ฟังก์ชัน `compute_vault_address_multisig` ใน `mobile-signer-ffi/rust` จึงตรวจเองสองข้อก่อนเรียก vault-core: (1) ปฏิเสธเมื่อ **public key** ซ้ำกัน แม้ chain code ต่างกัน เพราะผู้ถือ private key เดียวกันเซ็นแทนได้ทุก child ของ xpub ใดๆ ที่มี public key นั้น vault 2-of-3 ที่มีคีย์ซ้ำจึงถูกเซ็นโดยคนเดียวได้ (2) ปฏิเสธเมื่อปน mainnet กับ testnet **ขอ review จากเจ้าของ vault-core (descriptor)**: จะย้ายสองการตรวจนี้เข้า `build_multisig_descriptor` หรือไม่ — เป็นการเปลี่ยนพฤติกรรมของ `jade-ble`, `trezor-ble` และ `wallet-e2e` ที่เรียกฟังก์ชันนี้อยู่ ไม่ใช่ policy module แต่ตามกฎใน `AGENTS.md` การเปลี่ยน interface ของ vault-core ต้องเช็ค caller ก่อน ใน wrapper มี `TODO(vault-core descriptor owners)` ไว้ที่ `parse_and_check_xpubs` **เพิ่มเติมหลัง review (2026-10-20)**: (3) wrapper ปฏิเสธ key ที่ depth เกิน 253 และ string ที่ยาวเกิน 120 ตัวอักษร เพราะบน miniscript 13.1.0 (เวอร์ชันใน `Cargo.lock` ของเครื่องนี้ ซึ่งถูก git-ignore) `derive_address_at` คืน `Result` แต่ panic ได้จริง — วัดแล้ว depth 253 ผ่าน ส่วน 254 และ 255 ชน `unreachable!` ใน `miniscript-13.1.0/src/descriptor/key.rs:1269` ซึ่ง UniFFI รายงานเป็น `InternalException` ฝั่ง Kotlin ส่วน miniscript 13.2.0 (เวอร์ชันที่ clone ใหม่ resolve ได้ เพราะ vault-core ขอแค่ `miniscript = "13"`) คืน error ธรรมดาแทน panic (วัดแล้วที่ depth 254 และ 255) ขอให้เจ้าของ vault-core ตั้ง floor `miniscript = "13.2"` เพื่อให้ caller ที่ยังไม่มี guard (jade-ble, trezor-ble, wallet-e2e) ไม่ชน panic บน lockfile เก่า ส่วนข้อ (1) ตรวจได้แค่คีย์เดียวกันถูกใส่สองครั้ง ไม่ได้พิสูจน์ว่าเป็นคนละ signer: child ของคีย์ที่อยู่ในลิสต์หรือ account อื่นจาก seed เดียวกันมี public key ต่างกันจึงผ่าน และจาก xpub อย่างเดียวตรวจไม่ได้ ต้องใช้ key origin หรือ master fingerprint ตอน enroll ถ้าย้ายการตรวจเข้า vault-core: miniscript 13.1.0 มี `Descriptor::xkey_network()` (คืน `XKeyNetwork::Mixed` เมื่อปน network) สำหรับข้อ (2) ส่วน `Descriptor::sanity_check()` จับได้เฉพาะ key ที่เหมือนกันทุกไบต์ (`has_repeated_keys` เทียบ `DescriptorPublicKey` ทั้งตัว รวม chain code) จึงไม่จับสำเนาที่เปลี่ยน chain code

30. **ข้อแตกต่างของแต่ละแพลตฟอร์มที่อ่านจาก source (ส่วนของ Android วัดบน Galaxy S25 FE แล้วตามที่ระบุในแต่ละข้อ ส่วนที่ไม่ได้ระบุยังเป็นการอ่าน source)** (2026-10-21)

61. **หน้า Backup Words (board 1.4) ไม่มีคำเตือนเรื่องลบแอป แอปเพิ่มให้เองเป็นค่าเริ่มต้นรอทีมออกแบบตรวจ** (เปิด 2026-11-03) หน้า Key Created มีบรรทัด "ลบแอปแล้วกระเป๋าในเครื่องนี้จะหาย · กู้คืนได้ด้วย 24 คำเท่านั้น" อยู่แล้ว (ไม่มีบน board 1.3 เช่นกัน) แต่ผู้ใช้ที่เห็น 24 คำคือคนที่ต้องรู้ข้อนี้มากที่สุด จึงใส่บรรทัดเดียวกันใต้แบนเนอร์ใต้ตารางคำ (`backup_delete_warning`) เมื่อกระเป๋าบันทึกในเครื่องแล้ว ไม่ได้แก้ board ทีมออกแบบควรตัดสินว่าจะวางตรงไหนและใช้ถ้อยคำไหน ยังไม่ได้ดูเลย์เอาต์บน iPhone
62. **สอง `SingleSigWallet` ในกระบวนการเดียวกันไม่ใช้ตัวกันจ่ายซ้ำร่วมกัน** (เปิด 2026-11-03) ตัวกัน `unconfirmedSend` อยู่ในแต่ละอินสแตนซ์ของ `SingleSigWallet` ถ้ามีสองอินสแตนซ์พร้อมกัน (เกิดได้เฉพาะ Android และ `launchMode=singleTask` ที่ตั้งไว้กันกรณีนี้อยู่แล้ว) อินสแตนซ์หนึ่งส่งเงินแล้วผลไม่แน่ชัด อีกอินสแตนซ์ยังไม่รู้และอาจส่งซ้ำได้ การเก็บแบบ compare-and-swap (commit `053898e`) กันไม่ให้อินสแตนซ์เก่าเขียนทับสำเนาที่ใหม่กว่า แต่ไม่ได้ทำให้ตัวกันในหน่วยความจำของสองอินสแตนซ์ตรงกัน ทางแก้ที่เล็กที่สุดคือถือตัวกันไว้ที่ตัว session ที่อินสแตนซ์ใช้ร่วมกัน หรือให้เหลืออินสแตนซ์เดียวต่อกระบวนการ ยังไม่ได้ทำ ความเสี่ยงต่ำเพราะ `singleTask` และไม่มี `android:process` ใน manifest (`AndroidManifestTest` ล็อกไว้)
63. **compare-and-swap ของที่เก็บกระเป๋ายังพิสูจน์บนเครื่องจริงไม่ได้จากเทสต์ล้วน** (เปิด 2026-11-03) เทสต์ล้วนครอบคลุมการตัดสินใจของที่เก็บ ตัวนับ และ session แต่ไม่ครอบคลุม Keychain และ Keystore จริงภายใต้ Replace ที่ล้าสมัย รอบโทรศัพท์ต้องทำ (1) บน iPhone การเขียนทับจาก `wallet.b` ไป `wallet.a` ซึ่งมีแต่ simulator ที่เคยรัน (2) บน POCO Replace หนึ่งครั้งหลังปลดล็อก (3) ลำดับสองอินสแตนซ์ตามที่ `docs/10` ระบุไว้ใต้สิ่งที่แต่ละแพลตฟอร์มยังค้าง
64. **ข้อค้นพบจาก interrogate 2026-11-03 ที่แก้แล้ว** (เปิด 2026-11-03) รีวิวแบบปรปักษ์สามโมเดล (`.audit/phase2-interrogate-2026-11-03.md`) พิสูจน์ปัญหา 15 ข้อบนทางส่งเงินของกระเป๋ากุญแจเดียว ข้อที่แก้แล้วมีดังนี้ หมายเลขข้อตามรายงาน commit ดู `git log` **ฝั่ง Rust (commit `6001f64`):** จำนวนต่ำกว่า 546 sat ถูกปฏิเสธ และค่าธรรมเนียมที่สูงกว่าจำนวนส่ง ต่ำกว่า 1 sat/vB หรือสูงกว่า 2,000 sat/vB ถูกปฏิเสธ (ข้อ 5 และ 7) เงินทอนที่ต่ำกว่า 546 sat ทำให้การส่งถูกปฏิเสธแทนการรวมเข้าค่าธรรมเนียมโดยไม่บอก (ข้อ 6) ผลรวม UTXO ตรวจ overflow (ข้อ 8) outpoint ซ้ำถูกปฏิเสธ (ข้อ 9) การสแกนหยุดที่ 200 ที่อยู่ต่อสายและรายงานว่าประวัติผิดปกติ (ข้อ 10 และส่วนหนึ่งของข้อ 4) คำตอบของ explorer ที่ขัดแย้งกันเองเป็น error (ข้อ 11) ใช้เฉพาะเหรียญที่ยืนยันแล้ว (ข้อ 14) และ `hot_send` แยกเป็น `hot_prepare_send` ที่เซ็นโดยไม่ส่ง กับ `hot_broadcast` ที่ส่งอย่างเดียว **ฝั่ง Kotlin (commit ถัดจาก `6001f64` ดู `git log`):** (ข้อ 1) `SingleSigWallet.broadcast` เรียก `hot_prepare_send` แล้วบันทึก `unconfirmedSend` ลงเครื่องผ่าน `OnboardingSession.recordUnconfirmedSend` ก่อนเรียก `hot_broadcast` ทุกครั้ง ถ้าบันทึกไม่สำเร็จแอปไม่ส่งและแจ้ง "บันทึกสถานะการส่งไม่ได้ จึงยังไม่ส่ง ลองใหม่ภายหลัง" ส่งสำเร็จหรือ node ปฏิเสธจึงล้างตัวกัน `BroadcastUnknown` คงตัวกันไว้ `hot_send` เดิมถูกลบออกจาก Rust และ bindings (ข้อ 2) กฎ settle 120 วินาทีตามนาฬิกาเครื่องถูกถอด ตัวกันหายเมื่อประวัติที่โหลดสำเร็จมี txid หรือผู้ใช้กดล้างเองเท่านั้น หน้า Send และ Review มีลิงก์ "ตรวจแล้วว่ายังไม่ออก ส่งใหม่ได้" (`unconfirmed_clear`) ที่โผล่เมื่อตัวกันอายุครบ 120 วินาทีตามนาฬิกาเครื่องหรืออายุติดลบ กดแล้วเห็น txid แบบย่อ ข้อความ "กดต่อเมื่อตรวจใน explorer แล้วว่าไม่มีธุรกรรมนี้ ถ้าส่งไปแล้วจะจ่ายซ้ำ" ปุ่ม "ยืนยันส่งใหม่" (`unconfirmed_clear_confirm`) ที่ล้างทั้งหน่วยความจำและสำเนาในเครื่อง และ "ยกเลิก" (`unconfirmed_clear_cancel`) นาฬิกาตัดสินแค่เวลาที่เสนอปุ่ม ไม่เคยล้างเอง ข้อความทั้งหมดเป็นค่าเริ่มต้นรอทีมออกแบบตรวจ และยังไม่ได้ขับบน simulator
