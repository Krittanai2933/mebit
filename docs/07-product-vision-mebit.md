# mebit — วิสัยทัศน์โปรดักต์ฉบับปรับใหม่ (north star)

เอกสารนี้บันทึกการปรับ framing รอบใหญ่ที่เกิดจากการไล่ทวนความคิดใหม่ทั้งหมด **เอกสาร 01–06 ในชุดนี้ยังใช้ได้อยู่** แต่ตอนนี้ควรอ่านในฐานะ "สเปคของขา lending" ซึ่งเป็นแค่ 1 ใน 3 ขาของโปรดักต์ mebit ไม่ใช่ตัวโปรดักต์ทั้งหมด

## สิ่งที่เปลี่ยนไปจากกรอบคิดเดิม

เดิมเราคุยกันในกรอบ "เปิดบริษัทปล่อยกู้เงินบาทค้ำด้วย BTC แล้วต้องมี wallet ประกอบ" — กรอบนี้กลับหัวกลับหาง ตัวจริงคือ **mebit เป็นโปรดักต์บิตคอยน์สำหรับคนไทย ที่มี wallet/custody เป็นฐาน แล้ว lending เป็นแค่ฟีเจอร์ต่อยอดหนึ่งใน 3 ฟีเจอร์**

## โครงสร้างผลิตภัณฑ์ 3 ขา

1. **Wallet / Custody-as-a-service** — ตัวสินค้าหลัก ต้องเป็น Bitcoin wallet ที่ใช้ง่ายสำหรับคนทั่วไป (mass market) พร้อมความสามารถสร้าง/นำเข้า multisig สำหรับคนที่ต้องการความปลอดภัยระดับสูงขึ้น (แนวทาง Casa) — ไม่บังคับ ใครมาใช้แบบกระเป๋าเดี่ยวเฉยๆ ก็ได้
2. **Buy-sell** — ซื้อ/ขาย BTC แบบ OTC/brokered (ไม่ใช่ order book exchange เต็มรูปแบบ) เป็นฟีเจอร์ต่อยอดจาก wallet
3. **Lending** — ปล่อยกู้ค้ำด้วย BTC ตามที่ออกแบบละเอียดไว้ใน `01-06` เป็นฟีเจอร์ต่อยอดอีกชั้น ใช้ vault คนละชุดจาก custody vault ส่วนตัว

**ความสัมพันธ์ระหว่าง 3 ขา**: ยังไม่ตัดสินใจ (บังคับ onboarding ผ่านขาไหนก่อน หรือแยกอิสระให้เลือกเข้าขาไหนก็ได้) — เก็บเป็น open item

**MVP priority ที่เลือกไว้ตอนนี้**: เริ่มจาก Wallet/Custody-as-a-service ก่อน เพราะเป็นฐานที่อีก 2 ขาต้องพึ่งพา (มี BTC ใน custody ก่อนถึงจะ buy-sell หรือ pledge ค้ำกู้ได้)

## โมเดลกุญแจ: Nunchuk-first, Casa-style เป็นออปชันเปิดเผย

คำถามสำคัญ: mebit ควรถือกุญแจของลูกค้าไหม? สรุปจากการคุย:

- **Default = แบบ Nunchuk** — mebit เป็น pure coordinator ไม่ถือกุญแจลูกค้าเลยสักตัว ผู้ใช้ประกอบ M-of-N multisig ด้วยกุญแจของตัวเองทั้งหมด (มือถือ, hardware wallet, seed อื่น) แอปแค่ช่วยแสดงยอด + สร้าง PSBT ให้แต่ละอุปกรณ์ไปเซ็นเอง — ตรงกับหลัก self-custody จริงที่เป็นแกนของทั้งโปรเจกต์ และ**ไม่มีความเสี่ยงกฎหมายเรื่อง custodian ผูกอยู่**เพราะซอฟต์แวร์ไม่แตะ private key ของใคร
- **Optional add-on = กุญแจสำรองจาก mebit (แนวทาง Casa)** — ระหว่างสร้าง/นำเข้า vault มีตัวเลือกเปิดเผยชัดเจนให้เพิ่มกุญแจสำรองของ mebit เป็นอีก 1 ใน N ใครอยากได้บริการกู้คืน/ความสบายใจก็เลือกได้ ใครไม่อยากมี mebit เกี่ยวข้องเลยก็ปฏิเสธได้ตั้งแต่ต้น
- **นัยสำคัญ**: คำถามกฎหมายเรื่อง custodian (ที่ตัดออกจากการคุยไปก่อนหน้า) ตอนนี้ผูกอยู่กับ**เฉพาะฟีเจอร์เสริมที่คนเลือกเอง** ไม่ใช่ฟีเจอร์หลักของ multisig อีกต่อไป — ลดพื้นที่เสี่ยงกฎหมายของฟีเจอร์ default ลงไปมาก

## App flow ที่ปรับใหม่ (v3 — เวอร์ชันล่าสุดที่ยืนยันแล้ว)

หลักการ: onboarding เบา ใช้ได้ทันทีสำหรับทุกคน, Home เป็นจุดรวมทางเลือกที่น้ำหนักเท่ากัน ไม่มีอะไรถูกบังคับ

1. **Onboarding** (คืนกลับใกล้ดีไซน์เดิม ไม่ต้องเพิ่มขั้นตอน): Splash → Seed backup → Face ID — seed ตัวนี้ใช้เป็นรากได้ทั้ง single-sig (hot wallet) และเป็นกุญแจหนึ่งใน multisig vault ในอนาคต ไม่ต้องมี seed คนละชุด
2. **Home** — hub รวมยอด (hot spending / custody vault / collateral ที่ล็อกใน loan) พร้อม 4 ทางเลือกน้ำหนักเท่ากัน: Receive, Send, Buy/Sell, Borrow
3. **สร้าง Vault** (สมัครใจ แต่โผล่ให้เห็นตั้งแต่วันแรกเคียงข้างกับทางเลือกอื่นบน Home ไม่ซ่อน ไม่บังคับ) แตกเป็น 2 ทางย่อย:
   - **สร้างใหม่** — mebit ช่วย generate/เพิ่ม cosigner ทีละตัว → เลือกจะรวมกุญแจสำรอง mebit ด้วยไหม → Vault Health Check
   - **นำเข้า Vault ที่มีอยู่** — ผู้ใช้ paste/สแกน xpub หรือ descriptor ที่มีอยู่แล้ว (เช่นจาก hardware wallet หรือแอปอื่น) เข้ามาทีเดียว เลือก threshold (2-of-3, 3-of-5 ฯลฯ) mebit ประกอบ descriptor ให้ทันที — กรณีนี้มักไม่มีกุญแจ mebit เลย แอปทำหน้าที่ watch-only coordinator ล้วนๆ
4. **ทางลัดสำหรับคนที่ตั้งใจมาทำ multisig ตั้งแต่แรก** — หลัง Face ID ผ่านแล้วเจอ Home ครั้งแรก มี prompt เบาๆ ครั้งเดียวถามว่า "จะใช้แบบไหน" (กระเป๋าง่ายๆ / สร้าง Vault หลายกุญแจเลย) ถ้าเลือกอย่างหลังเด้งตรงเข้าขั้นตอนสร้าง Vault ทันที ไม่ต้องผ่าน Home แบบง่ายก่อน — เป็นทางลัด ไม่ใช่ gate ใหม่ ไม่เลือกอะไรก็เข้า Home ปกติ
5. **Borrow → Loan Dashboard → Repay → Success** — ของเดิมจากเอกสาร 01-06 เกือบไม่เปลี่ยน แค่ลดสถานะจาก "หัวใจของแอป" เป็นหนึ่งในทางเลือกบน Home
6. **Bottom nav**: Activity (ledger รวม), Portfolio (รวมทั้ง 3 ประเภทยอด ไม่ใช่แค่ loan), Settings (จัดการคีย์/cosigner ของทุก vault)

*(แผนภาพ v1–v3 ถูกวาดเป็น artifact ในระหว่างการสนทนาแล้ว — เอกสารนี้สรุปเป็นข้อความสำหรับอ้างอิงและแก้ไขต่อ)*

## นัยต่อสถาปัตยกรรม backend (vault-core)

`vault-core` (Rust, descriptor + policy + PSBT) ที่ออกแบบไว้สำหรับ lending vault โดยเฉพาะ ต้อง**generalize เป็น policy template ที่สลับได้** แทนการ hardcode 2-of-3 แบบ lending อย่างเดียว เพราะตอนนี้ต้องรองรับ policy อย่างน้อย 3 แบบภายใต้ engine เดียวกัน:

- **hot wallet** — single-sig ไม่มี policy พิเศษ
- **personal custody vault** — M-of-N ที่ผู้ใช้กำหนดเอง (2-of-3, 3-of-5 ฯลฯ) อาจมีหรือไม่มีกุญแจ mebit ก็ได้
- **lending vault** — 2-of-3 คงที่ (ผู้กู้/แพลตฟอร์ม/ผู้ให้กู้) พร้อม policy enforcement ตามที่ออกแบบไว้แล้วใน `01-architecture-overview.md`

ทั้งหมดนี้ยังใช้ `bdk` Rust core เป็นฐานได้เหมือนที่แนะนำไว้ใน `06-mobile-app-design-mebit.md` — bdk รองรับทั้ง single-sig, multisig แบบกำหนด descriptor เอง, และ watch-only อยู่แล้ว

## สิ่งที่ยังไม่ตัดสินใจ (เพิ่มจาก `04-open-items.md`)

1. ความสัมพันธ์ระหว่าง 3 ขา — บังคับ onboarding ผ่านขาไหนก่อน หรือแยกอิสระให้เลือกเข้าขาไหนก็ได้
2. ขอบเขต Buy-sell แบบ OTC/brokered ในรายละเอียด (ใครเป็นคู่สัญญาซื้อขาย, ราคาอ้างอิงจากไหน) — ยังไม่ได้ออกแบบเลย
3. เงื่อนไข/ราคาของกุญแจสำรอง mebit แบบ Casa-style (ฟรีหรือ subscription, สิทธิ์การกู้คืนทำงานอย่างไร)
4. ผลกระทบทางกฎหมายของกุญแจสำรอง mebit (ผูกกับข้อ 3) — ยังตัดออกจากการคุยตามคำขอเดิม แต่ตอนนี้ขอบเขตเสี่ยงเล็กลงเพราะจำกัดอยู่แค่ฟีเจอร์เสริม
