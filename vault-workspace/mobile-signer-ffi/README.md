# mobile-signer-ffi

**Owner**: person 4 — `docs/00-capstone-brief.md` §3.6.

**Depends on**: `vault-core` for the vault-signer half. The generalized multisig API has landed and the Kotlin bindings expose it. The three-party functions still sit on `vault-core` mocks, and UI/UX work does not wait for either. Recommended to depend on `bdk` (Bitcoin Dev Kit, Rust core) for the hot-wallet half — see below.

## This is two wallets in one app

The borrower's BTC is always either **free** (not pledged to any loan) or **pledged** (locked in a specific loan's 2-of-3 vault). That means this module is genuinely two layers, not one:

1. **Hot wallet (single-sig)** — for free BTC. A real Bitcoin wallet: address generation, UTXO tracking, fee estimation, send/receive, its own node connectivity (Electrum/Esplora, not routed through the backend), and watch-only PSBT construction. **Recommended: build on `bdk` Rust core** rather than hand-rolling this — it supports all of the above natively. Do not use `bdk-rn`/`bdk-dart` wrappers (integration-testing-only as of July 2026).
2. **Vault signer (multisig)** — for pledged BTC. The original scope: wrap `vault-core`'s key derivation and PSBT signing behind UniFFI.

Both need to read as one balance on Home/Portfolio in the UI, but the key/signing logic stays clearly separated underneath — see `../../docs/01-architecture.md`'s "mobile-signer-ffi is two wallets in one app" section and `../../docs/04-open-items.md` (items 2 and 9) for the open questions here.

**Current status: the vault-signer half and Bluetooth for two hardware wallets have code.** Both are callable from Kotlin through UniFFI, see [Kotlin bindings](#kotlin-bindings-uniffi-and-gobley) and [Bluetooth](#bluetooth-jade-and-trezor-safe-7). The hot-wallet half hasn't been started — see `../../docs/05-progress-and-next-steps.md`.

## Getting started

### Rust crate

```
cargo test -p mobile-signer-ffi
```

The crate exports four synchronous functions through UniFFI: `derive_borrower_pubkey`, `compute_vault_address`, `sign_psbt` and `compute_vault_address_multisig`, plus the Bluetooth exports described in [Bluetooth](#bluetooth-jade-and-trezor-safe-7). Its golden addresses are re-derived by `scripts/address_oracle.py`. The four functions are the **vault-signer half only**. The **hot-wallet half** (`bdk`-based) hasn't been started, and that is the single biggest gap in this module right now.

### Kotlin bindings (UniFFI and Gobley)

The Rust crate reaches Kotlin through [UniFFI](https://mozilla.github.io/uniffi-rs/) 0.29.4 and the [Gobley](https://github.com/gobley/gobley) 0.3.7 bindgen, which generates Kotlin Multiplatform code. Gobley's Gradle plugins do not run under the Kotlin Toolchain, so `scripts/ffi.sh` runs the bindgen directly. The generated files are committed in the `app/mobileSignerFfi` module. The Android and the iOS file are bindgen output plus one scripted patch, `scripts/patch_bindings.py` (see [Pitfalls found](#pitfalls-found)), and nobody edits them by hand. They compile under the Toolchain's Kotlin 2.4.20, although Gobley 0.3.7 was built against Kotlin 2.1.10.

#### What Kotlin gets

The package is `com.mebit.ffi.signer`.

| Kotlin function | Result |
|---|---|
| `computeVaultAddressMultisig(xpubs: List<String>, threshold: UByte): String` | A real address. It is the first receive address of `wsh(sortedmulti(threshold, <xpub>/0/*, ...))`, built by `vault-core`. `xpub` keys give `bc1...` and `tpub` keys give `tb1...`. Throws `MobileSignerException`. |
| `computeVaultAddress(borrowerPubkey: String, platformPubkey: String, lenderPubkey: String): String` | **Mock.** The three-party lending vault. Returns `tb1q` plus a hash from `vault-core`'s mock descriptor, which is not a Bitcoin address. |
| `deriveBorrowerPubkey(accountXpub: String, index: UInt): String` | **Mock.** Returns `<accountXpub>/m/48'/0'/0'/2'/<index>`, which is not a public key. |
| `signPsbt(psbtJson: String, borrowerPubkey: String): String` | **Mock.** Returns `MOCK_SIG[<loan_id>:<output count>:<borrowerPubkey>]`. It signs nothing and does not run the policy engine. Throws `MobileSignerException.InvalidPsbtJson` for JSON that is not an `UnsignedPsbt`. |

`computeVaultAddressMultisig` always returns index 0 and takes the network from the key prefix, because its fixed two-argument signature has no room for either. Another index, the change chain or regtest needs a new function. `tpub` keys cover testnet, testnet4 and signet, which all give the same `tb1...` string. Regtest (`bcrt1...`) cannot be produced.

Before it calls `vault-core`, `computeVaultAddressMultisig` checks the keys one at a time, in list order, and the first bad key decides the error. It rejects:

- A string longer than 120 characters, before it decodes the string.
- A key deeper than 253 levels. Under miniscript 13.1.0 `derive_address_at` panics on such a key, and under 13.2.0 it returns an error. This check gives both the same `InvalidXpub`.
- A SLIP-132 key (`zpub`, `Zpub`, `vpub`, `ypub`). Convert it to `xpub` or `tpub` first.
- A list that mixes `xpub` and `tpub` keys.
- A list that holds one public key twice, even under a different chain code.

`vault-core` accepts the mixed and the repeated lists (`docs/04-open-items.md` item 28). The threshold and key-count rules run after every key has passed, so a list of 21 keys with one repeat reports the repeat. The repeat check catches one key entered twice. It does not prove that the keys belong to different signers, because a child of a listed key, or a second account from one seed, has a different public key.

#### Errors

Every fallible function throws a subclass of `MobileSignerException`. The error is flat, so the list index appears only inside `message`, and `message` equals the Rust error's `Display` text.

| Subclass | Thrown when | `message` |
|---|---|---|
| `InvalidPsbtJson` | `signPsbt` gets malformed JSON | `invalid PSBT json: ` followed by the `serde_json` text. The prefix is unchanged from before UniFFI. |
| `InvalidXpub` | a key is not a base58 `xpub` or `tpub`, is longer than 120 characters, or is deeper than 253 levels | `key at index 1 is not a valid xpub or tpub: ` followed by the parser's text or the length, or `key at index 0 is too deep to derive addresses from: depth 254, the maximum is 253`. It never contains the key. |
| `NetworkMismatch` | the list mixes `xpub` and `tpub` keys | `key at index 2 is for a different network than key at index 0 (xpub is mainnet, tpub is testnet)` |
| `DuplicateXpub` | two keys share one public key | `key at index 2 is the same as key at index 0` |
| `InvalidThreshold` | the threshold is 0 or above the key count, or the list is empty or has more than 20 keys | `vault-core`'s text, for example `invalid multisig threshold: invalid threshold 4-of-3; cannot have k > n` |
| `VaultCore` | any other `vault-core` failure | `vault-core`'s text |

The bindings also define `InternalException`, which UniFFI throws for an unexpected error such as a Rust panic. It is not a `MobileSignerException`, so a caller that must not crash catches both. No known input triggers it. A binding that is out of date with the Rust enum can also throw a plain `RuntimeException`.

#### Types

| Rust | Kotlin |
|---|---|
| `&str`, `String` | `String` |
| `u32` | `UInt` |
| `u8` | `UByte` |
| `Vec<String>` | `List<String>` |
| `Result<T, MobileSignerError>` | `T`, annotated `@Throws(MobileSignerException::class)` |

`Int.toUByte()` wraps without an error, so `300.toUByte()` is 44. Check a threshold's range before you convert it.

#### Build and test

Run the commands from `vault-workspace/mobile-signer-ffi`. You need macOS for `build`, `test` and `apk`.

1. Install the prerequisites.
   - Rust with four targets: `rustup target add aarch64-apple-ios aarch64-apple-ios-sim aarch64-linux-android x86_64-linux-android`
   - `cargo install cargo-ndk`. Version 4.1.2 is the one tested.
   - NDK 27.1.12297006: `sdkmanager --install 'ndk;27.1.12297006'`. `ANDROID_HOME` (or `ANDROID_SDK_ROOT`) must point at the SDK, or the SDK must sit at `~/Library/Android/sdk`.
   - Xcode with an iOS simulator runtime.
2. Run `scripts/ffi.sh build`. Run it once per clone and after every change under `rust/`, `vault-core/`, `jade-ble/` or `trezor-ble/`. It installs the pinned bindgen into `vault-workspace/target/tools`, builds the Rust libraries for the host, iOS and Android, regenerates the Kotlin bindings, patches them, and stops when an assertion fails. Commit the generated files it changes.
3. Run `scripts/ffi.sh test`. It runs `build`, then `cargo test`, then the Kotlin tests on the Android host JVM and on an iOS simulator. It refuses to start while a simulator is booted.
4. Run `scripts/ffi.sh check` before you commit a Rust change. It regenerates the bindings in a temporary directory, applies the patch, and diffs the four generated files against the committed ones. It also diffs the vendored btleplug Java and `THIRD_PARTY_NOTICES.md` against the btleplug that cargo resolves. It writes nothing under `app/` or `rust/` and needs `cargo` and `python3`. Only macOS was tried.

Three more commands are optional. `scripts/ffi.sh bindings` regenerates only the committed Kotlin, without the iOS and Android builds. Use it to refresh what you commit, or on a host that cannot run `build`. It leaves the iOS and Android libraries as they were, so run `build` before any Kotlin test of a changed export or doc comment. On macOS it does refresh the host test library. Only macOS was tried. `scripts/ffi.sh apk` copies the Android libraries into `app/androidApp/jniLibs/`. `scripts/ffi.sh clean` removes the files `build` and `apk` staged outside git and keeps the installed bindgen and the host build. `python3 scripts/address_oracle.py` re-derives the golden multisig addresses from the constants in `rust/src/lib.rs` without `vault-core`, using only the Python standard library. `python3 scripts/test_patch_bindings.py` tests `patch_bindings.py`: it patches exactly once and fails closed. `build`, `check` and `test` run both scripts.

Plain `./kotlin build` and `./kotlin test` include `mobileSignerFfi`, so they fail until `ffi.sh build` has run. `ffi.sh build` needs macOS, so on another OS nothing stages the host test library and `./kotlin test` cannot pass. That is inferred from the code, and no run happened there. On a fresh clone, `./kotlin build` stops at the link task of an iOS test target (`linkIosArm64TestDebug` or `linkIosSimulatorArm64TestDebug`, whichever fails first) with `Undefined symbols`, and `./kotlin test -p android` fails with `UnsatisfiedLinkError: Unable to load library 'mobile_signer_ffi'`. Scope the commands to one module, for example `./kotlin build -m androidApp` or `./kotlin test -m shared -p android`, and they do not need the Rust libraries.

To use the library from an app module, add `- //mobileSignerFfi` to its `dependencies`. `shared` does, so `androidApp` and `iosApp` get it. For Android, run `scripts/ffi.sh apk` once as well, because the library reaches an APK only from `androidApp/jniLibs/`. An APK built without it has no native library, and the first call fails with `UnsatisfiedLinkError`. After that, every `ffi.sh build` refreshes those copies. Decide `settings.android.abiFilters` first. The library exists only for `arm64-v8a` and `x86_64`, so the Toolchain warns about the other ABIs, and a filter drops 32-bit devices from the whole app. For iOS, every build that includes the module needs the Rust libraries, so developers must run `ffi.sh build` before they build the app.

#### Pitfalls found

**The generator**
- **Gobley ignores a misplaced config.** `rust/uniffi.toml` needs its keys at the root of the file, and `--config` must name it. Without them the bindgen exits 0 and writes only the common file. `ffi.sh` fails when the four expected files are not all there. The file also pins `cdylib_name`, because without it the generated `findLibraryName` follows the name of the library file the bindgen reads.
- **Rust and Kotlin must match.** Every exported signature, and every `///` doc comment on an export, feeds a UniFFI checksum. Android checks it when the library loads and throws `UniFFI API checksum mismatch`. The iOS generated code never checks it, so stale bindings pass on iOS. `MobileSignerError` has no checksum at all, and Kotlin reads its variants by position. Reordering a variant, or inserting or removing one before the last, makes both platforms throw the wrong subclass, and nothing reports it. Appending one throws a plain `RuntimeException`. `cargo test` fails when a function's checksum differs from the committed Android file. Only `ffi.sh check` sees an enum change or an iOS-only drift, so run it after every change.
- **Doc comments reach Kotlin as KDoc.** A `/*` or `*/` inside a `///` line breaks the generated file, because Kotlin block comments nest. `ffi.sh` fails before it generates.
- **A leftover file named like generated output breaks the Kotlin build.** A renamed or copied `mobile_signer_ffi.*` file redeclares the generated objects, and the compiler errors point into the generated code. `ffi.sh` fails on such a file in the four generated folders. Files with other names are left alone.
- **Gobley's async wrapper leaks when the caller is cancelled first.** The generated `uniffiRustCallAsync` frees the Rust future in a `finally` inside `withContext(Dispatchers.IO)`. The caller has already made the Rust call by then, and the future owns a reference to the Rust object. `withContext` throws without running its block when the caller is already cancelled, or is cancelled while the block waits for an IO thread. The `finally` never runs, so the future and the object leak. A link the object owns would then stay up until the app exits, which is inferred from the code and was not observed on a device. `scripts/patch_bindings.py` replaces the whole function in the Android and the iOS file with a copy whose `finally` sits outside `withContext`. `withContext` returns or throws only after its block has ended or was never started, so the one free runs exactly once on every path (read from the `kotlinx.coroutines` 1.11.0 JVM bytecode, and tested on the JVM, see below). `rust_future_free` consumes the handle, so a second free would be a use-after-free. UniFFI's own Kotlin template frees on the caller's side the same way. The script changes nothing and fails `ffi.sh` unless it finds Gobley 0.3.7's text exactly once in each file, and `scripts/test_patch_bindings.py` tests that, so an upgrade cannot pass silently: review the leak, then update or delete the script. `check` compares the committed files with the patched output. Two Kotlin tests guard the fix. `WalletLinkCancelTest` fails without the patch (`expected: <0> but was: <1>` on the Android host JVM, `Expected <0>, actual <1>` on an iOS simulator, measured). `AsyncWrapperFreeTest` runs on the Android host JVM, calls the wrapper with fake lambdas and counts the frees on five paths: finished, failed, cancelled while Rust is pending, already cancelled, and cancelled while the block is queued behind a saturated `Dispatchers.IO`. Against Gobley's original function the last two fail (frees 0, not 1). A deliberate double free fails the counting test (frees 2) and crashes the JVM in the integration test, and a wrapper that never frees fails six tests. The iOS function has the same text, so that test is not repeated there, and Kotlin/Native's `withContext` is read from the same common source, not run.
- **The versions are coupled.** Gobley 0.3.7 is built on UniFFI 0.29.4. `Cargo.lock` is git-ignored, so `rust/Cargo.toml` pins `uniffi = "=0.29.4"`. `ffi.sh` fails when that pin differs from its own constant or when the installed bindgen is not 0.3.7. The link between Gobley 0.3.7 and UniFFI 0.29.4 comes from the bindgen's install log and nothing checks it, so bump all three together.

**The Kotlin Toolchain**
- **The cinterop `.def` must sit in `cinterop@ios/`.** A `cinterop/` folder at the module root is ignored when android is a platform, and the iOS build then reports hundreds of unresolved references.
- **`libraryPaths` must be absolute.** cinterop runs with the Kotlin/Native install directory as its working directory and expands no variables. So the header-only `mobile_signer_ffi.def` is committed, and `ffi.sh build` writes `mobile_signer_ffi_link.def` per machine. Git ignores that file.
- **The Toolchain does not rebuild the cinterop klib when only the `.a` changes.** Without a hash line in the link def, iOS tests run old Rust and report no error. `ffi.sh` writes the hash and replaces the def only when its text changed, because a new mtime alone costs a rebuild.
- **`jniLibs/` in a library module is ignored.** Only `androidApp/jniLibs/<abi>/` reaches an APK.
- **Dependencies are not transitive.** `mobileSignerFfi/module.yaml` lists `kotlinx-coroutines-core` and `androidx.annotation` itself, because the generated code and btleplug's Java need them and a module that depends on it does not inherit them.
- **JNA needs two artifacts.** The device needs the AAR. The host JVM test needs the plain JAR, because the AAR has no desktop natives. The test loads the host library from `testResources@android/darwin-aarch64/` (`darwin-x86-64` on an Intel Mac), which git ignores, and JNA finds it by name.
- **A failing iOS test run leaves its simulator booted.** `ffi.sh test` refuses to start while any simulator is booted, and after a failing run it shuts down only the simulators booted since just before the iOS run. Do not boot a simulator during that run.

**The native builds**
- **cargo-ndk picks the newest NDK unless `ANDROID_NDK_HOME` is set.** On the machine used here that is an r29 beta. An empty `ANDROID_NDK_HOME`, which some shells export, makes cargo-ndk fail. `ffi.sh` sets the variable to the pinned NDK itself.
- **The 16 KB alignment comes from cargo-ndk.** Plain `cargo` with the same NDK links at 0x1000, and 16 KB page-size devices cannot load that. `ffi.sh` asserts 0x4000 on every `LOAD` segment.
- **Build the iOS libraries for iOS 15.0, in their own target directory.** Kotlin/Native links its test executable at 15.0, and the Xcode project targets 18.2. Without the setting, the C objects carry the SDK default and the link warns once per object. `ffi.sh` checks every object's minimum version with `otool -l`, because `vtool` does not read an archive.

**The behavior**
- **`vault-core` accepts duplicate and mixed-network xpubs, and miniscript 13.1.0 panics on a deep one.** Under miniscript 13.1.0, `derive_address_at` hits an `unreachable!` for a key at depth 254 or more, which UniFFI turns into `InternalException`. Miniscript 13.2.0 returns an error instead (measured on both). `Cargo.lock` is git-ignored, so one machine can hold 13.1.0 while a fresh clone resolves 13.2.0. The wrapper rejects all three cases under both versions, and `docs/04-open-items.md` item 28 asks the `vault-core` owners to take the checks over and to require miniscript 13.2.
- **Dependency text can change.** `Cargo.lock` is git-ignored, so a fresh resolve can reword the `miniscript`, `bitcoin` and `serde_json` messages. The tests assert the wrapper's own texts exactly and the dependency texts by prefix. A fresh resolve with no lockfile (miniscript 13.2.0, serde_json 1.0.154) passes all 17 tests.
- **The generated Android file exposes helper types.** Gobley makes `FfiConverter*`, `RustBuffer` and similar types public. The Rust side cannot hide them.

#### Synchronous calls

The four functions above are synchronous. In Kotlin they are ordinary functions, not `suspend` functions, and each call blocks its thread until Rust returns. They do CPU-only work. Valid input returns fast, since the whole Rust test run takes 0.07 s. Base58 decoding is quadratic, though. A 100,000-character string took 7.3 s in a release build before the wrapper started rejecting any string over 120 characters. Call them off the main thread if a call could ever take long. The Bluetooth calls that talk to a wallet are the asynchronous ones. They are `suspend` functions, described in [Bluetooth](#bluetooth-jade-and-trezor-safe-7).

### Bluetooth: Jade and Trezor Safe 7

The crate also exports Bluetooth for two hardware wallets, through the `jade-ble` and `trezor-ble` crates. Rust owns the radio on both platforms (`../../docs/08-multisig-wallet-spec.md` §5.1), on btleplug 0.13.3. Kotlin gets the generated API below. There is no screen and no facade. A removable [probe](#the-hardware-probe) exercises the API.

#### What Kotlin gets

The package is `com.mebit.ffi.signer`.

| Kotlin | Does |
|---|---|
| `scanWallets(kind: WalletKind): List<FoundWallet>` (suspend) | Scans for 4 seconds and lists the wallets of that kind in range. Cancelling stops the scan. |
| `WalletLink(wallet: FoundWallet)` | Makes a link that is not connected yet. Use it as `WalletLink(found).use { ... }`, because `close()` starts the disconnect. |
| `WalletLink.connect(codes: PairingCodes)` (suspend) | Connects, pairs if the wallet needs it, and checks the wallet is what it says. A link connects once, so make a new one after a failure or a cancel. Cancelling leaves nothing that `close()` cannot end: measured with a Jade on two phones, unit-tested with a fake central for a Safe 7. |
| `WalletLink.info(): WalletInfo` (suspend) | A Jade answers `get_version_info`. A Safe 7 returns the identity it gave during `connect`. |
| `WalletLink.disconnect()` (suspend) | Ends the link and waits until it is down. |
| `PairingCodes.pairingCode(): String?` (suspend, you implement it) | Returns the six digits a Safe 7 shows while pairing, or null to give up. It must not throw. A Jade never asks. |
| `liveWalletLinks(): ULong` | How many `WalletLink` objects exist in this process. It is for tests and not a stable API: a link that a call kept alive after `close()` still counts. |

`WalletKind` is `JADE` or `TREZOR_SAFE7`. `FoundWallet` holds `kind`, `id` and `name`, and both crates select a wallet by them, so pass a `FoundWallet` that a scan returned. `WalletInfo` holds `name`, `firmware` and `details`. `details` is `WalletDetails.Jade` (`board`, `state`, `networks`) or `WalletDetails.TrezorSafe7` (`internalModel`, `deviceId`, `label`, `mtu`).

What the calls promise:

- **One task per link.** A task owns the device and `WalletLink` sends it requests. A cancelled `info()` stops only the wait: the wallet finishes the exchange and the link stays usable. A request whose caller left before the task reached it never goes to the device.
- **`disconnect()` and `close()`.** `disconnect()` waits for a request in flight, then for the link to be down, and it waits the same way when a failure or another call is already ending the link. It does nothing until `connect` has returned, so cancel a `connect` that is still running instead. `close()` starts the disconnect once no call is still running on the object, because a call in flight holds it, and it returns before the link is down. Cancel the call, then close, and use `disconnect()` when you must wait.
- **Cancel and cleanup.** A cancelled scan stops scanning, which fake-central unit tests prove and no radio test does. A cancelled `connect` leaves nothing that `close()` cannot end (measured with a Jade, unit-tested with a fake central for a Safe 7). A failed Safe 7 `connect` disconnects before it returns, and a failed or cancelled Jade `connect` disconnects in the background, so a retry right after can race it. `WalletLink(found)` exists before `connect` starts, so a cancel at any moment leaves an object that `close()` can end. A function that returned the link would lose it: UniFFI drops the result of an async call that Kotlin cancelled after Rust finished.
- **A call on a coroutine that is already cancelled throws and leaves nothing behind.** So `use {}` or `close()` still releases the link after a cancel. Gobley's wrapper used to leak the Rust call in that case, and `scripts/patch_bindings.py` now fixes it, see the generator pitfalls. A call that must run after a cancel, such as `disconnect()` to wait until the link is down, goes in `withContext(NonCancellable)`.
- **Testnet only.** The network is fixed to testnet4 until an export needs the choice.
- **No secret leaves Rust.** A Safe 7 pairing credential holds the host's private key. It is dropped after `connect`, so every `connect` asks for the code (`../../docs/04-open-items.md` item 20).

#### Bluetooth errors

Every Bluetooth call throws a subclass of `BleException`. The error is flat. `message` is the vendor crate's own text, and the subclass says what to do.

| Subclass | Thrown when |
|---|---|
| `Unsupported` | The build has no Bluetooth backend, or on Android `System.loadLibrary` did not run before the first call. |
| `PermissionDenied` | The OS refused Bluetooth to the app. Android: ask for the permissions again. iOS: Settings. |
| `BluetoothOff` | btleplug has no usable adapter. On Android that is Bluetooth fully off or missing (read from the Android sources, not run). An adapter that stays in `BLE_ON` after the switch is turned off gives `NotFound` instead (measured on a Galaxy S25 FE). iOS never throws it (read from the source). Ask the platform whether Bluetooth is on before you scan. |
| `NotFound` | No wallet of that kind was seen, or the `FoundWallet` has an empty name or id. A scan that Android refused (the throttle in Known limits) gives it too, and so does Bluetooth off on iOS (read from the source) or on an Android adapter in `BLE_ON`. The text says whether anything was seen at all. On Android 11 and below it also means a missing location permission or Location switched off. |
| `WrongDevice` | Not a wallet this app supports: another Trezor model, older firmware, a device without the wallet service. |
| `PairingCancelled`, `PairingFailed` | The user gave up, or the Safe 7's own button ended pairing. Pairing failed for another reason, including an OS pairing that was declined or not confirmed in time, which iOS reports this way with advice in the text (measured with the Safe 7). Android reports that case as `Disconnected` while connecting. |
| `BondRemoved` | The wallet forgot this phone's Bluetooth bond. Forget the wallet in the phone's Bluetooth settings and pair again. Measured with the Safe 7 on macOS (it had forgotten the Mac after a restore) and on an iPhone 15 (it had forgotten the phone), and measured with the Jade on macOS (it had evicted the Mac). On an Android 11 phone the same situation, with the Safe 7 on Pair new device, ended in one pairing dialog and a working link, with no error. |
| `Refused` | The wallet declined, or the request was not sent. The link stays usable. A second `connect` on one `WalletLink` also lands here. |
| `Timeout`, `Disconnected`, `Link` | The wallet did not answer in time. The link is down or closed. Any other Bluetooth failure. While connecting, a `Disconnected` text says that a pairing request may not have been confirmed in time, because Android reports a declined pairing only as a dropped link (measured with the Safe 7 and with the Jade). |
| `Protocol` | A bug, or a wallet out of step with this app. Connect again and report it. |

Kotlin reads the variants of `BleException`, and the fields of every exported record and enum, by position. Append new ones and run `scripts/ffi.sh build`. `InternalException` covers a Rust panic and an exception thrown by your `PairingCodes`.

#### Platform setup

**iOS.** `iosApp/src/Info.plist` holds `NSBluetoothAlwaysUsageDescription`. The app's final link needs `-framework CoreBluetooth`, because the Rust library is static and Xcode does that link. `scripts/ffi.sh` writes `linkerOpts = -framework CoreBluetooth` into the generated link def. Without it the app fails to link with six undefined `_CBAdvertisementData...` and `_CBCentralManagerScanOption...` symbols. The module's own iOS test links without it, so only an app link, such as `verify.sh ios-start`, catches the omission.

**Android.** `androidApp/src/AndroidManifest.xml` declares `BLUETOOTH` and `BLUETOOTH_ADMIN` (up to API 30), `ACCESS_FINE_LOCATION` (up to API 30), `BLUETOOTH_SCAN` with `neverForLocation`, `BLUETOOTH_CONNECT`, and `bluetooth_le` as not required. `blePermissions(sdk)` and `missingBlePermissions(context)` in `shared/src@android/com/mebit/app/ble` say what to ask for at run time: `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` from API 31, `ACCESS_FINE_LOCATION` below. `locationOffBlocksScans(context)` is true on API 30 and below while Location services are off. A missing permission and Location off each end a scan in `NotFound`, not in an error (measured on Android 11, see What was checked), so check both before you scan. No product screen asks yet, because this phase adds no UI. `MainActivity` asks only when the debug probe starts, and shows the `RequestMultiplePermissions` pattern to copy. Call `loadBleLibraryIfPackaged()` (same package, so deleting the probe keeps it) first in `onCreate`. It runs `System.loadLibrary("mobile_signer_ffi")`, so ART calls the library's `JNI_OnLoad`, which starts btleplug. JNA's own load never calls `JNI_OnLoad`, and without it every Bluetooth call throws `Unsupported`. btleplug's 28 Java files are copied into `mobileSignerFfi/src@android` by `ffi.sh`, `ffi.sh check` diffs them against the crate, and their licences are in `THIRD_PARTY_NOTICES.md`. `androidApp/proguard-rules.pro` keeps them and JNA, and tells R8 to ignore JNA's AWT classes. A release build fails without that last rule.

#### Known limits

Unless a limit says measured, it was read from the code or from the btleplug source and was not run.

- **The Safe 7 ran on one iPhone 15 and one Android 11 phone, a few runs each, with firmware 2.13.0.** It has not run on the Galaxy S25 FE (Android 16) or on any other phone, and its authenticity is unchecked. The cancel guards of `trezor-ble` have run on hardware on those two phones only.
- **Each scan and connect opens its own CoreBluetooth manager.** btleplug never frees one, so every call parks a thread and an idle manager until the app exits. Sharing one adapter would list stale devices, and clearing its list disconnects links, so that needs a per-scan filter proven on hardware.
- **Android shares one adapter for the process.** `scan_wallets` and `connect` clear what it remembers first. On a Galaxy S25 FE a Jade unplugged between two scans was not listed by the second, but no run left the clear out, so it is not proven to be the reason. Two scans that overlap still collide on its single scan callback, and a cancelled scan's stop can end the next scan. Scan one wallet kind at a time, and do not scan while another call connects.
- **Cancelling in the instant `connect` finishes is safe, but a task that panics is not.** A panic inside the link task drops the device without a disconnect, so the operating system link stays up until the app exits. `disconnect()` then returns early.
- **A failed `disconnect()` cannot be retried.** The crates consume the device on disconnect, so after a timeout the link may stay up.
- **The scan window is 4 seconds and fixed.** Both crates scan again inside `connect`.
- **Android refuses an app's sixth scan start within 30 seconds,** and a refused scan looks like an empty one. Measured on a Galaxy S25 FE: five starts passed in 15.5 seconds and the sixth, 19.5 seconds after the first, got `status=6`, and `connect` then threw `NotFound` with the Jade in range. The 30 second window is the documented one, not measured. `scanWallets` and every `connect` each start a scan and first clear the shared device list, so space them. The probe's retry loop waits 4 seconds between scans for this reason.
- **`NotFound` is also what Bluetooth switched off, a missing permission and Location off can give.** On an Android adapter in `BLE_ON` (Bluetooth switched off while the phone's `ble_scan_always_enabled` is 1) the scan finds nothing and `jade` throws `NotFound` after about 6 s. That is measured on a Galaxy S25 FE, where the platform also logged a swallowed `SecurityException` for `BLUETOOTH_PRIVILEGED`, and on the POCO X3 NFC. `BluetoothOff` needs an adapter that is fully off: with Bluetooth and Bluetooth scanning both off, the POCO's adapter was `OFF` and `jade` threw `BluetoothOff: No Bluetooth adapter available` after 70 ms (measured). On Android 11 and below a missing `ACCESS_FINE_LOCATION` and Location services off each give an empty scan, so `NotFound` (measured on the POCO in all four combinations), where Android 12 and newer threw `PermissionDenied` for a permanent denial (measured on the Galaxy). `missingBlePermissions` and `locationOffBlocksScans` tell an app which cause it has before it scans. iOS scans nothing with Bluetooth off (read from the source, not run). A screen that wants a turn-Bluetooth-on prompt asks the platform itself.
- **The first pairing on Android waits for a person.** On the Galaxy the first `info` returned 24.5 seconds after `connected`, while the phone showed two dialogs. Give that call room. On the POCO the pairing request is a heads-up notification that lasts a few seconds. When nobody tapped, the bond went from BONDING to NONE 30 s after the request and `jade` threw `Disconnected: Not connected` 3 s later (measured with the round-three build). For the Safe 7 the library adds a hint about an unconfirmed pairing request to that text. For the Jade it does so only when the drop falls inside the connect steps, and on the POCO it fell after them in two runs on 2026-10-24 (`docs/04` item 39).
- **The probe's `cancel` mode (the probe was removed on 2026-10-25) does not prove the radio stopped scanning.** `cancel-connect` does show a leaked link on Android, because `connect` clears the cached device list first: without the link guard the Galaxy found no Jade for 36 seconds.
- **Every Safe 7 `connect` needs the user twice.** The OS asks to pair on the first connect from a host (a Pairing Request on iOS, a heads-up notification and a dialog on Android). Then the Safe 7 asks "Allow mebit on mebit iPhone to pair?" (the name differs by platform) and shows six digits, on every connect, because the library drops the credential on purpose (`docs/04` item 20). If nobody confirms the OS pairing, iOS returns `PairingFailed` with advice after about 36 s (measured with the Safe 7), and Android returns `Disconnected` with a hint about a pairing request after about 10 to 30 s (measured with the Safe 7 and the Jade). Tell the user which screens to watch before you connect.
- **A Safe 7 can stay unreachable after an unconfirmed pairing.** On the iPhone the next launch timed out connecting (`Timeout: timed out connecting`, 50 s) to a Safe 7 that the scan listed and that still showed Pair new device. Leaving that screen and opening it again fixed it. That is one occurrence, and the cause is inferred.
- **The Safe 7 changes its address, and a host that is not bonded to it sees a new id.** The suffix changes each time Pair new device is opened (6T5, 7G0, 9A5 and 1A1 in one afternoon). A host that is bonded keeps one id through suffix changes (the iPhone's `c529a0b3…` through three suffixes in 1.3 hours, the Mac's `197161c7…` for ten minutes). A host that is not bonded sees a new id under the same suffix. The iPhone saw it 14 s after its first scan and the Mac 20 s after its first scan, with nobody touching the Safe 7. The Android logs of round three also show a changed address under one suffix (43 s), without a connect. The wrapper sets `device_is_hint`, so a stale id falls back to the only Safe 7 in range, and several Safe 7s in range still end in `NotFound`. A natural stale id was measured on the Mac (strict `NotFound`, hint connects) and on the iPhone (it connects, and the use of the fallback is inferred from the code path). Before round five every successful `connect` found the id of the scan before it, and within one session the id held across scans 10 to 14 s apart, so the change is not regular. In round three the iPhone, not bonded yet, listed four different ids in eight minutes (11:47 to 11:55). The cause is not established. The controller firmware enables privacy (`CONFIG_BT_PRIVACY=y`) and restarts advertising 30 s after each start (`nordic/trezor/trezor-ble/src/ble/advertising.c`, core v2.13.0). That fits the 33 s of one Mac sample. No source that was read shows that the restart draws a new address, and no address timeout setting was found.
- **An awake Safe 7 was found every time on the phones, but not on the Mac.** Fourteen 4 s scans in 12 phone runs, in pairing mode and on its home screen, all found it. With the Mac bonded, one of three 10 s scans found it, and with no bond at all and the Safe 7 idle, 36 four-second Mac scans found nothing. An asleep Safe 7 turns its Bluetooth off (`docs/05`), so a phone cannot see it. Tell the user to wake it.
- **After a cancelled connect the Jade needed 12 s to be seen again on the POCO.** In five of five `cancel-connect:jade` runs the first 4 s scan after the cancel found nothing and the second found it, where the Galaxy and the iPhone needed 4 s and the Safe 7 needed 4 s on the POCO. The cause is not known. A caller that gives up after one 4 s scan reports `NotFound` here.
- **A Jade keeps few bonds.** After the POCO paired, the Mac's bond was gone and the iPhone's was not. The Mac's connect now ends in a typed `BondRemoved` with advice (measured). Forget the Jade in macOS Bluetooth, then connect again and confirm the pairing on the Jade.
- **MIUI 12.5 blocks `adb install`, `pm grant`, `settings put` and `pm clear`** while its USB debugging (security settings) switch is off. Install from the Files app and change permissions, Location and Bluetooth by hand. MIUI also hides a dialog behind the app that was in front when an activity starts from the background.
- **The error classification matches English text on iOS and macOS.** CoreBluetooth hands btleplug only `localizedDescription`, so a phone in another language shows the raw `Link` text, as before the change (inferred, tested on English devices only).
- **`NotFound` right after a good scan happened once.** On the POCO with the Safe 7 on Pair new device, the probe's scan saw it and the rescan inside `connect` 4 s later saw no Safe 7 (2 devices seen). A strict mismatch and an absent Safe 7 print the same text, so that case could have been a changed address, which the fallback now handles. The fallback cannot help when no Safe 7 is in range.
- **The Safe 7's paired-devices list keeps the first host name that each Bluetooth address sent.** After the prompts changed to `mebit iPhone` and `mebit Android`, the list still showed `mebit mobile` twice and `desktop` for the Mac, 3 entries in all (the user's reading of the screen). The Safe 7 firmware (core v2.13.0) explains it. After the user approves the "Allow … to pair?" prompt, it stores the host name and app name for the host's Bluetooth address, and it skips the write when that address is already stored (`apps/thp/pairing.py:117-121`, `trezor/wire/thp/paired_cache.py:62-70`). The list is the bond list joined to that store by address (`apps/homescreen/device_menu.py:25-32`). "Forget this device" removes only the bond (`apps/management/ble/unpair.py:55`), and the store is pruned only when a new address is stored (`paired_cache.py:41-42`). On the Mac, two fresh pairings under the host names `probe-A` and `probe-B` showed their live names in the prompt and left the Mac's entry at `desktop` and `mebit trezor-hw-test` (measured). A new host name therefore reaches only addresses that the Safe 7 has not stored, so choose the final name before the first user pairs. After a wipe every address is new to the Safe 7, and the first pairing of each host stored its current name (measured 2026-10-24, see What was checked). A wipe is the only remedy that was measured. Whether a new address prunes the name of a host that was forgotten on the Safe 7 was not measured, because no spare host was available. Recovery restores neither names nor bonds, because the seed holds only the wallet and the credential key comes from a random device secret that a wipe replaces. Two phones of one platform still share a name.
- **A declined or unanswered Jade pairing carries a pairing hint on iOS, macOS and Android.** Cancel on the iPhone's request ends as `Timeout: timed out discovering services. If a pairing request was waiting…` (20.4 s), and a reject on the Jade as `Disconnected: the Jade dropped the link while connecting. If a pairing request was waiting…` (iPhone 8.6 s, Mac 17 s with a 5 s scan). On Android the Jade holds its pairing request in the first write after `connect`, and only that write can get the hint. On the POCO (Android 11) a reject, a hands-off run and a Jade unplugged during the pairing all ended as the hint (15.3 s, 31.2 s and 16.7 s after `connected`). A later request on the same link stays the plain `Disconnected`. The kinds stay `Timeout` and `Disconnected`, and the text is conditional. It cannot tell a rejected pairing from a Jade that lost power: a bonded Jade unplugged before its first request gave the same hint. A write that fails with a raw Android status (`Unable to write characteristic, status: N`) is not hinted. The 60 s `FirstWriteTimedOut` never fired on hardware, and no other Android version was measured. A Safe 7 rejected at the comparison screen on an iPhone, or cancelled on the iPhone's dialog, ends as the typed `PairingFailed` (round seven).

```
cd vault-workspace/mobile-signer-ffi/app

```
