# Movie Page keys + critical boards

A user opens Add Key from the keyring's +, picks one of four cards, confirms a key's fingerprint with one tap (the ไม่ตรง link saves nothing), and reaches the keyring. Critical boards T13–T15 are reachable from hardware demo and catalog.

## Sub-features

- `mp-keyring` (Penpot 2.1) shows the title, a subtitle counting the keys, a navy + on the title row and one card per key with a monogram tile, its name, "source · fingerprint" and a pill ยืนยันแล้ว or ยังไม่ยืนยัน. Unconfirmed keys come first (6.2's order and subtitle). A ⋯ at each card's right end opens a floating menu (2.1.A1 to A3) that deletes the key after a confirm (2.1.9), or shows a grey ลบกุญแจ and the reason it cannot.
- `mp-add-key-four-options` (Penpot 2.2) shows one list of four cards in this order: this phone, another mebit phone, hardware wallet with the Jade and Trezor Safe 7 chips, and import with the 24 tile. The bottom bar shows with the Keys tab lit.
- `mp-hw-scan` lists the Jade and Safe 7 found nearby, or says none was found.
- `mp-verify-mismatch` discards the staged key and returns to the screen it came from.
- `mp-t13-unsupported` shows Unsupported Model from hardware demo.

## How to get to it (user POV)

- Catalog → ADD KEY, or the Keys tab → the + on the title row (`id:cta_keyring_add`). Home's upgrade card (`id:cta_s1_vault`) opens the keyring too.
- Hardware → จำลองรุ่นอื่น (Unsupported) → T13.
- Confirm Key → ไม่ตรง · กลับไปเชื่อมต่อ (ไม่บันทึก) → back to the connect screen, or to the pairing screen for a key from another mebit. T14 opens only from the catalog row VERIFY KEY · Fingerprint ไม่ตรง.

## Driving it with verify.sh

Preconditions:

- App running; prefer catalog jump for isolation.

- **Keyring.** `verify.sh ios-tap "id:tab_keys"`, `verify.sh ios-see "id:screen_keys/keyring"`, `verify.sh ios-see "id:keyring_subtitle"` (reads "N กุญแจในคลัง · ยืนยันแล้วทั้งหมด", or "N กุญแจ · ยังไม่ยืนยัน k ใบ (ขึ้นก่อน)" while a key is unconfirmed, and `id:keyring_empty` with no key). One `id:key_<id>` per key, a merged node whose label holds the name, the "source · fingerprint" line, the tile text (iOS on an iPhone, AND on Android, MB for a key from another mebit phone, JD, TRZ) and the pill. A phone wallet whose backup was skipped shows ยังไม่ยืนยัน and is listed first. Each card's ⋯ is `id:cta_more_<id>`, a node of its own beside the merged `id:key_<id>`. On a saved key no several-key wallet uses, its menu holds `id:menu_delete_<id>` (ลบกุญแจ), which opens `id:dialog_delete_key` with `id:cta_delete_key_confirm` and `id:cta_delete_key_cancel`, and the confirm deletes the key with no owner check. A delete that cannot be saved keeps the key and shows `id:delete_failed` (ลบกุญแจไม่สำเร็จ ลองอีกครั้ง) under the subtitle until a ⋯ opens again. With no wallet saved, as on a start with only hardware keys, a key no several-key wallet uses is offered only while the saved book's store holds nothing, as after a Forget or on a first run. A store that still holds a book, or one that cannot be read, blocks it as a book that cannot be read. On a key a several-key wallet uses, on a wallet's own `onboard_` key and while the saved book cannot be read, the menu holds `id:menu_blocked_<id>` with the grey ลบกุญแจ and its reason: ลบไม่ได้ · กุญแจนี้ใช้อยู่ใน plus the wallets' names, ลบไม่ได้ · เป็นกุญแจของ plus the wallet's name and · ลบที่หน้า Wallet แทน, or ลบไม่ได้ในตอนนี้ · อ่านรายการ Wallet ไม่ได้. On Android the menu is its own window, where tags are not resource ids, so tap ลบกุญแจ by its text. `id:cta_delete_<id>`, `id:cta_keyring_vault` and the vaults notice are gone. Shot `mp-keyring`.
- **Add Key.** Open catalog (`id:open_catalog`), tap the ADD KEY row (`id:catalog_keys/add` or text containing `ADD KEY`), or from the keyring `verify.sh ios-tap "id:cta_keyring_add"`, then `verify.sh see "id:screen_keys/add"`. The four cards are `id:cta_add_this_device`, `id:cta_add_mebit_other`, `id:cta_add_hardware` and `id:cta_add_import`, from the top down in that order. `id:tab_keys` and `id:tab_wallets` show, so the bar is on. Shot `mp-add-key-four-options`. The first and last cards add a wallet and the middle two add a key for a Vault.
- **Hardware scan.** From Add Key `verify.sh ios-tap "id:cta_add_hardware"`, or from Key Source `verify.sh ios-tap "id:cta_hardware"`, then `verify.sh ios-see "id:screen_keys/hardware"` and `verify.sh ios-see "id:hw_none_found"`. Shot `mp-hw-scan-empty`: a simulator has no Bluetooth, so the scan ends with the pill "Bluetooth เปิดอยู่ · ไม่พบอุปกรณ์", the line `id:hw_none_found` and the link `id:cta_hw_rescan`. `verify.sh ios-tap "id:cta_hw_rescan"` and `verify.sh ios-see "id:hw_none_found"` run the scan again. A real Jade or Safe 7 in range adds a row with its own เชื่อม button (`id:cta_hw_jade` or `id:cta_hw_trezor`). That needs the device on a phone and is not recorded here yet. Verified on the simulator for the empty state.
- **Add Key, hardware.** From Add Key, `verify.sh ios-tap "id:cta_add_hardware"`, `verify.sh ios-see "id:screen_keys/hardware"`, `verify.sh ios-tap "id:cta_hw_demo_jade"` twice (the demo buttons are below the first screen, so the first tap only scrolls the button into view), `verify.sh ios-see "id:screen_keys/verify"`, `verify.sh ios-tap "id:cta_verify_match"`, `verify.sh ios-see "id:screen_keys/keyring"`, `verify.sh ios-see "text~:Jade · จำลอง"`. Shot `mp-addkey-hw-keyring`. A demo key is saved with "· จำลอง" after its name, and its keyring card reads that name, the line "Jade · <fingerprint>", the tile JD and the pill ยืนยันแล้ว. This path ends at the keyring alone, with no back chip, and so does the same match from Key Source, see [onboarding](./movie-page-onboarding.md). From the keyring `verify.sh ios-tap "id:cta_keyring_add"` returns to Add Key. Verified on the simulator. On 2026-11-11 the end on the keyring alone ran for a pasted key from Add Key and for a hardware start from Key Source (run `20261111-005741-ios`). The demo Jade from Add Key has not run again.

- **Mismatch (mebit on another phone).** From Add Key, `verify.sh ios-tap "id:cta_add_mebit_other"`, `verify.sh ios-tap "id:cta_pair_demo"`, `verify.sh ios-see "id:screen_keys/verify"`, `verify.sh ios-tap "id:cta_verify_mismatch"`, `verify.sh ios-see "id:screen_keys/pair-mebit"`. - **T14.** `verify.sh ios-tap "id:open_catalog"`, `verify.sh ios-see "id:catalog_keys/add"`, `verify.sh ios-tap "id:catalog_critical/t14"` twice (the first tap scrolls the sheet), `verify.sh ios-see "id:screen_critical/t14"`, `verify.sh ios-see "id:mismatch_message"`. ## Gotchas

- Confirm Key is one tap. `id:cta_verify_match` saves the staged key under the name in `id:verify_key_name`, and there is no typed check (docs/04 item 41). The link `id:cta_verify_mismatch` discards the key.
- The demo buttons `id:cta_hw_demo_jade`, `id:cta_hw_demo_trezor` and `id:cta_hw_unsupported` sit below the first screen of the hardware screen. The first `ios-tap` only scrolls them into view, so tap again.
- Pair another mebit by pasting three lines (fingerprint, xpub, path) or BSMS 1.0 into `id:pair_paste`, then `id:cta_pair_paste`. `id:cta_pair_demo` still stages a fixture key when the run has no paste. No QR. docs/04 item 26.
- The paste takes only a BIP48 Native SegWit multisig key: a tpub at `m/48'/1'/N'/2'` whose own depth and child number match that path. Anything else, such as a BIP44, 49, 84 or 86 path, a ypub, zpub, upub or vpub, a Nested `1'` ending or a mainnet key, stages nothing and shows a Thai line in `id:error` that starts ใช้กุญแจนี้สร้าง Wallet แบบ Multisig (Native SegWit) ไม่ได้ and names the reason.
