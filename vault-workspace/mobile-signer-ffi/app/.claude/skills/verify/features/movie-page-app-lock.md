# Movie Page app lock

After onboarding the user turns on Face ID. From then on the app asks for Face ID again after more than a minute in the background, and before it signs a single-sig send. The text button uses the phone's own passcode instead.

## Sub-features

- `mp-lock-enable` turns the lock on with a Face ID scan.
- `mp-lock-failed` shows the failed state with the attempts left.
- `mp-lock-unlock` shows the unlock screen when the app comes back after a minute.
- `mp-lock-sign` asks for Face ID before a send is signed.
- `mp-lock-unavailable` says so where nothing can scan.

## How to get to it (user POV)

- Create or import a key, then the App Lock screen. The unlock screen and the sign check come later, from using the app.

## Driving it with verify.sh

Preconditions:

- A simulator can play Face ID. Enrol once per simulator: `xcrun simctl spawn booted notifyutil -s com.apple.BiometricKit.enrollmentChanged 1`, then `xcrun simctl spawn booted notifyutil -p com.apple.BiometricKit.enrollmentChanged`. Answer a pending scan with `xcrun simctl spawn booted notifyutil -p com.apple.BiometricKit_Sim.pearl.match`, or `.pearl.nomatch` for a miss.
- The scan prompt and the passcode sheet are iOS's own, outside the app's accessibility tree. XCUITest cannot tap or type into them, so a simulator run never taps ใช้รหัส 6 หลักแทน: on a simulator it opens the passcode sheet and stays there.
- A real scan on the phone needs the iPhone 15, with you in the loop: the phone unlocked, plugged in, Developer Mode on, Settings, Developer, Enable UI Automation on, Face ID enrolled. Start with `VERIFY_IOS_DEVICE=<udid> VERIFY_IOS_TEAM=<team id> VERIFY_IOS_BUNDLE_ID=com.<you>.mebit.verify VERIFY_IOS_KEEP_APP=1 verify.sh ios-start`. The first launch is refused until the developer is trusted (Settings, General, VPN & Device Management); run `ios-start` again after that. Export the same variables for every later `verify.sh` call, and say what is about to happen before each step so the person holding the phone is ready.
- On the phone, the person taps and scans, and the agent only takes `ios-shot` while a Face ID or passcode sheet is up. Every `ios-tap`, `ios-see`, `ios-type` and `ios-gone` starts a test run that wakes the app, and iOS cancels the sheet when that happens. Navigate with `ios-tap` first, then hand over.
- Do not loop over command strings in zsh with `set -- $s`: it does not split and `verify.sh` just prints its usage. Write each command out.

- **Unavailable.** Neither platform reaches it with a screen lock set. On Android the prompt accepts the PIN, so Enable turns the lock on (see Android below). On a simulator a created wallet no longer reaches this state. The iOS store saves it, so Enable reads the saved copy back, and without Face ID enrolled that opens iOS's passcode sheet, which a simulator run cannot answer. An imported wallet is saved the same way (not run).
- **Enable (simulator).** Enrol, then `verify.sh ios-tap "id:cta_enable_lock"`, `notifyutil … pearl.match`, `verify.sh ios-see "id:screen_vaults"`. Shot `mp-lock-enabled`. For a saved wallet the card is the store reading the saved copy back, still one card.
- **Miss (simulator).** After a pending scan, `pearl.nomatch` shows iOS's own "Face Not Recognized" sheet with Try Face ID Again and Cancel. The app's failed state (`id:lock_failed`, board 1B.5.1) only shows once iOS reports the second miss, which a simulator run cannot reach. A later `pearl.match` still completes the pending scan.
- **Unlock on return (simulator).** With the lock on and the app at Home, `xcrun simctl launch booted com.apple.Preferences` leaves the app. Wait 65 s, then `xcrun simctl launch booted com.mebit.app`. `verify.sh ios-see "id:screen_unlock"` passes and the Face ID sheet is up. After `pearl.match`, `verify.sh ios-gone "id:screen_unlock"` and `verify.sh ios-see "id:screen_vaults"`. Shot `mp-lock-unlock`.
- **Sign check (simulator).** From the Wallet list: `verify.sh ios-tap "id:card_spending"`, `verify.sh ios-tap "id:cta_s1_send"`, `verify.sh ios-tap "id:cta_s4_review"`, `verify.sh ios-see "id:screen_send/s5"`, `verify.sh ios-tap "id:cta_s5_sign"`. The Face ID sheet shows over the review screen and nothing is signed: `verify.sh ios-see "id:screen_send/s5"` still passes. Shot `mp-lock-sign`. After `pearl.match` signing goes on to the broadcast, and with the demo address and an empty wallet it ends in an error line under the button ("invalid PSBT json: base58 error"), not in S6.
- **Failed scan (phone).** On a fresh App Lock the person taps เปิดใช้ Face ID, covers their face, taps Try Face ID Again, and covers it once more. The app then shows `id:lock_failed`: the title "Face ID ไม่ผ่าน", an orange ring on the tile, and the FACE ID · FAILED box. iOS counts misses across attempts, including cancelled ones, and locks Face ID out after five. The first phone run went straight to the lockout: the screen read 5 misses and 0 left, and the primary button read "ใช้รหัส 6 หลัก". "2 misses, 3 left" after the first failed result is not confirmed on the phone. Shot `mp-lock-failed`.
- **Passcode (phone).** The person taps the passcode button (ใช้รหัส 6 หลัก or ใช้รหัส 6 หลักแทน), iOS's passcode sheet opens, and the correct code enables the lock, clears the Face ID lockout and goes to `id:screen_vaults`. Verified on the iPhone 15 while this step still ended on First Run Home. The passcode path has not run since the Wallet list replaced it.
- **Unlock on return (phone).** With the lock on and the app at Home, `xcrun devicectl device process launch --device <udid> com.apple.Preferences` leaves the app. Wait 70 s, then `xcrun devicectl device process launch --device <udid> com.<you>.mebit.verify` brings it back. The unlock screen and the Face ID sheet come up on their own, and the first scan starts at once, so the person must already be looking at the phone. A miss shows iOS's "Face Not Recognized" sheet. A match goes back to Home. Verified on the iPhone 15.
- **Sign check (phone).** Navigate with `ios-tap` up to `id:screen_send/s5`, then the person taps เซ็นและส่ง and scans. Signing continues to the broadcast, which fails for the demo address and empty wallet. On the iPhone 15 the screen then showed the raw text "invalid PSBT json: base58 error". It now shows the orange banner `id:error` (title ส่งไม่สำเร็จ, message ลองอีกครั้ง · ตรวจยอดคงเหลือก่อนส่งซ้ำ) and not the wallet's text. The banner was then verified on the iPhone 15 with a live empty wallet on 2026-10-31, see [send](./movie-page-send.md). A refused sign now shows `id:not_signed` (title ยังไม่ได้ส่ง) with the wallet's reason in place of `id:error`, worked out from the code and not run.
- **Refused sign (phone).** The Face ID sheet has no Cancel until a scan fails, and for signing a failed scan moves to iOS's passcode sheet. The person covers their face, then presses Cancel on the passcode sheet: `id:sign_refused` shows and nothing is signed. It was plain text "ยืนยันตัวตนไม่สำเร็จ ลองอีกครั้ง" when verified on the iPhone 15. It is now the orange banner of board 4.5.1 (title ส่งไม่สำเร็จ, message ยืนยันตัวตนไม่สำเร็จ ลองอีกครั้ง · ยังไม่มีอะไรถูกเซ็นหรือส่ง), and a refusal hides any earlier failed-broadcast banner. Verified on the iPhone 15 on 2026-10-31 with the banner: after a cancelled Face ID `id:sign_refused` shows, and after a later successful scan it is replaced by `id:error`, which is `id:not_signed` now for that empty wallet.
- **Android (emulator).** Set the PIN, create a key and Enable as in [wallet restart](./wallet-restart.md) ("Android saves the key"): one system prompt, the PIN, `id:screen_vaults`. Wait until `mCurrentFocus` names `BiometricPrompt` and then about 3 s more before `input text 1234`, or the digits land before the PIN field has focus and the sheet counts a wrong PIN (it stays up and takes the next try). Unlock on return: `verify.sh adb shell input keyevent 3`, wait 65 s, the `monkey` launch (the same pid, so the same process). The unlock screen shows and the prompt comes up by itself. The PIN gives `verify.sh gone "id:screen_unlock" 20` and `verify.sh see "id:screen_vaults"`. With the prompt up, `verify.sh adb shell input keyevent 4` cancels: `verify.sh see "id:cta_unlock"`, `verify.sh gone "id:lock_unavailable"`, and `mCurrentFocus` stays on `MainActivity`, so no second prompt. `id:cta_unlock` asks again. Sign check: the sign button needs a balance, and no explorer is reachable here, so apply the step 9 probe of the wallet-restart recipe, type the address and `0.005` on S4 (`tap "id:s4_address"`, `adb shell input text ...`), `tap "id:cta_s4_review"`, `tap "id:cta_s5_sign"`. The prompt comes up over S5. Back key: `id:sign_refused`, nothing signed. Again with the PIN: signing goes on and the probe's broadcast ends at `id:send_unknown`. Do not press the back key when no prompt is up, because it leaves the app. `logcat -d | grep "AuthSession: Dismissed"` shows `IsCrypto: true` for Enable (the store read-back) and `IsCrypto: false` for the lock and the sign check, `Error: 10` for a cancel. Verified on `Medium_Phone_API_36.0` (runs `20261103-032245` and `20261103-033125`). Enable and a cold start ending on `id:screen_vaults` ran again on 2026-11-11 (run `20261111-014648`), where tapping the prompt's `desc:PIN area` before `input text` was a reliable wait.

## Gotchas

- `ios-stop` removes the app from the phone and the developer trust goes with it. `VERIFY_IOS_KEEP_APP=1` keeps it.
- Android asks through the system prompt with a strong biometric or the screen lock, whatever the button says. A biometric-only sheet would need a cancel button and leaves a PIN-only phone nothing to answer with. Five wrong PINs come back as a cancel, so the unlock screen never asks again by itself. The screen still says Face ID on Android.
- Hardware wallets (`WalletLink.signWalletPsbt`) confirm on their own screen and are not gated by this lock.
- The 60-second lock is in memory and starts unlocked. A cold start with a saved wallet opens the unlock screen first, see [wallet restart](./wallet-restart.md). Android does the same from API 30 with a screen lock.
- Leaving the app with `simctl launch` of another app leaves a "‹ Settings" breadcrumb in the status bar. That is the simulator, not the app.
- `devicectl device capture screenshot` shows the whole screen, system sheets included, and does not wake the app. It is the only safe way to look while a sheet is up.
- After a key was created, App Lock shows the eyebrow "SECURITY · ขั้น 3 / 3" and no back chip (boards 1.3.1 and 1.6); after an import it shows neither. The failed state adds "SECURITY · Face ID ไม่ผ่าน" in the create flow (boards 1.3.1.1 and 1.6.1), which has only been checked by reading the code.
- On a simulator the app's failed state cannot be reached even with idb: five `pearl.nomatch` answers, each followed by an idb tap on iOS's Try Face ID Again, left the system sheet up and the app never reported a result.
